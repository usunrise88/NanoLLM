# Модуль автонастройки `nanollm optimize`: спецификация

Статус: реализовано в рабочем дереве (этапы 0–5 плана), проверка на машинах (§7) — в
`bench/results/rusunrisebook/optimize-2026-10-23/`; замеры этапа 0 — в `optimize-stage0-2026-10-23/README.md`
рядом. 2026-10-23. Факты и замеры, на которые опираются правила, лежат в
[AUTOTUNE.md](AUTOTUNE.md). Этот документ заменяет раздел «Единый механизм настройки (план; не реализован)»:
команда называется `optimize`, а не `tune`.

## 1. Что делает модуль

Пользователь выбирает один из трёх режимов работы. Модуль:

1. осматривает машину (железо, драйверы, диск, память, загрузку);
2. по оценкам без запуска модели отбрасывает варианты, которые не подходят режиму;
3. коротко меряет оставшиеся варианты (не дольше ~2 минут на типичном ноутбуке);
4. выбирает набор настроек и объясняет каждое решение;
5. сообщает о найденных проблемах (медленный диск, старый драйвер, батарея и т. п.);
6. записывает профиль, а сервер работает по нему.

Точки входа: TUI `nanollm optimize`, HTTP API и установщики `install.ps1` / `install.sh`.

**Права администратора не нужны ни на одном шаге, и модуль их не просит.** Всё, что требует повышения
(очистка standby-списка Windows, планы электропитания, лимиты мощности GPU), модуль не делает. Если такое
действие помогло бы, модуль советует его словами, а пользователь решает сам.

## 2. Режимы

Внутри режим — это набор ограничений и цель выбора. Наружу (CLI, API, установщик) видны только три имени:
`silent`, `optimal` и `powerful`. Свои лимиты извне задать нельзя.

| | Тихий (`silent`) | Оптимальный (`optimal`) | Производительный (`powerful`) |
| --- | --- | --- | --- |
| Устройства | только CPU | любые: GPU, iGPU, CPU | любые |
| Память процесса (§2.1) | минимальная, при которой выполняется порог скорости | ≤ 4 ГиБ по плану, по замеру ≤ 4 ГиБ + 200 МиБ | вся свободная память (правило `DerivedPreset`: RAM — ¾ свободной, VRAM — свободная) |
| Потоки decode / prefill | 2 / 2 | ≤ ⌊физические ядра / 2⌋, минимум 1, для обоих | все: decode — `DefaultThreads`, prefill — `DefaultBatchThreads` |
| Приоритет процесса | ниже обычного, на Windows ещё EcoQoS | обычный | обычный |
| Цель выбора | минимум памяти | максимум скорости (§3.4) | максимум скорости |
| Порог скорости | 1 ток/с | 1 ток/с | 1 ток/с |
| Контекст на слот, минимум | 4608 | 4608 | 4608 |

**Порог 1 ток/с общий.** Вариант медленнее 1 ток/с считается неработоспособным в любом режиме: модуль его
не выбирает и не предлагает. Порог проверяется на decode после промпта в 4096 токенов (эталон §3.4), а не
на пустом контексте.

**Минимальный контекст.** Эталонный запрос (промпт 4096, ответ 300, плюс разметка чата) должен помещаться в
любом режиме, поэтому нижняя граница контекста при автонастройке — 4608 токенов, а не 4096, как у
планировщика сейчас. Бюджет, которому не хватает памяти на 4608, кандидатом не считается.

**Физические ядра** считаются вместе с E-ядрами. Пример: у i7-12700H 6 P + 8 E = 14 ядер, значит в
оптимальном режиме 7 потоков. Decode на CPU упирается в память уже на 6 потоках, поэтому генерация почти
не теряет. Prefill медленнее примерно на 30 %: замер stage0 — 20 потоков 155–172 ток/с, 6 потоков 125–128.

**Тихий режим** нужен, чтобы за машиной можно было работать, пока модель отвечает. Поэтому:
- дискретная GPU и iGPU не используются: у GPU раскручиваются вентиляторы, а у iGPU самый маленький пресет
  уже 4 ГиБ;
- 2 потока;
- приоритет процесса ниже обычного (`BELOW_NORMAL_PRIORITY_CLASS` на Windows, `nice 10` на Linux и macOS;
  понижение прав не требует);
- на Windows EcoQoS (`SetProcessInformation`, `ProcessPowerThrottling`, `EXECUTION_SPEED`): планировщик
  ОС держит процесс на E-ядрах и на экономных частотах.

Из всех бюджетов, дающих ≥ 1 ток/с, выбирается самый маленький.

**Производительный режим при нехватке памяти.** Если свободно меньше 6 ГиБ, режим работает с тем, что есть:
те же лимиты памяти, что у оптимального, но все ядра. Об этом выводится сообщение (§3.5,
`mode_degraded`).

### 2.1 Что считается потреблением памяти

Потребление = **private bytes процесса** (память, которую ОС не может отобрать без выгрузки в своп) **плюс
VRAM, занятая процессом**, включая контекст драйвера. Страничный кэш файла модели не считается: ОС отдаёт
его другим программам сама. В отчёте он показан отдельной строкой.

На UMA (iGPU Intel, Apple) буферы GPU уже входят в private bytes: AUTOTUNE.md, «Приватные байты процесса на
UMA включают буферы Vulkan». Отдельно они не прибавляются.

Единицы: ГиБ и МиБ, как в пресетах (`ram-4g` = 4096 МиБ).

**Как это считается на Windows.** private — это приватный рабочий набор процесса (счётчики
`PROCESS_MEMORY_COUNTERS_EX2`, пик по выборке раз в 100 мс: ОС пика не хранит); закреплённые страницы файла
(range-lock) добавляются отдельно. Commit charge (`PrivateUsage`) для лимита не берётся: на дискретной GPU под
WDDM в него входит и видеопамять. VRAM процесса — `Dedicated Usage` из счётчиков PDH; на UMA считается только
private.

**Следствие для GPU.** Нынешний vram-4g (режим M2, vram-ple-host) занимает 3,3 ГБ VRAM, а таблица PLE
(1,5 ГиБ) и входной `token_embd` лежат в закреплённой памяти хоста. Вместе около 5,9 ГиБ, то есть в
оптимальный режим он не проходит. Под общий лимит 4 ГиБ на дискретной GPU подходит M3 (vram-ple-disk):
PLE и вход читаются из файла, и в private bytes их нет. Замер этапа 0 (§6): M3 на CUDA **не медленнее M2**
(tg 100,8 против 95,3 ток/с, pp 5645 против 5484) и при контексте 8192 держит 4,02 ГиБ (0,68 private + 3,34
VRAM). Процесс с контекстом CUDA или Vulkan держит ещё ~448 МиБ приватной памяти сверх плана: планировщик
прибавляет их при проверке общего лимита (`plan.GPUHostMemory`). Поэтому под лимитом режим M2 пропускается, а
из режимов полной выгрузки берётся тот, где вырос больший контекст.

## 3. Как работает

| Этап | Что происходит | Время |
| --- | --- | --- |
| 1. Осмотр | железо, драйверы, диск, загрузка, версии (§3.1) | ≤ 10 с |
| 2. Отсев | кандидаты из планировщика, отсев по лимитам и оценкам (§3.2) | мгновенно |
| 3. Замер | 1–2 загрузки модели, короткие пробы на каждой (§3.3) | ≤ ~100 с |
| 4. Выбор | по цели режима, проверка памяти по замеру (§3.4) | мгновенно |
| 5. Отчёт | решения с причинами, проблемы (§3.5) | — |
| 6. Сохранение | профиль, `tune.mode` в конфиге, перезагрузка модели (§3.6, §3.7) | секунды |

`--dry-run` проходит этапы 1, 2 и 5: показывает, что найдено, какие варианты возможны и их оценки, и ничего
не запускает.

### 3.1 Осмотр

Всё читается с обычными правами. Части, которые уже есть в `internal/hwinfo`, помечены «есть».

| Что | Как | Зачем |
| --- | --- | --- |
| CPU: модель, ядра P/E, потоки, ISA | есть (`hwinfo.Collect`) | потоки, лимит ядер |
| Вариант CPU в ggml и признаки (`multirow-q4_0`) | есть (бэкенд) | MTP на CPU, предупреждение `no_fast_kernels` |
| RAM: всего и **доступно сейчас** | `GlobalMemoryStatusEx.ullAvailPhys`; `MemAvailable` в `/proc/meminfo`; `vm_stat` | что поместится, `low_free_ram` |
| Память: скорость, число модулей | SMBIOS type 17 (скорость есть, число модулей — новое) | `single_channel` |
| Устройства GPU: тип, память всего/свободно, UMA, признаки (`cuda-nano`, `backend-sampling`, `fa-small-batch`), compute capability | есть (бэкенд) | кандидаты, правила |
| Драйвер GPU | NVIDIA — `nvidia-smi` (есть, `enrichGPUs`); Intel/AMD на Windows — `DriverVersion` и `DriverDate` из ключа класса дисплеев в HKLM (чтение доступно пользователю); Linux — версия из описания устройства Vulkan | `old_driver` |
| VRAM, занятая другими | total − free и список процессов из `nvidia-smi` (на WDDM только имена) | `vram_busy` |
| Диск, где лежит модель: тип | Windows — `IOCTL_STORAGE_QUERY_PROPERTY` (`StorageDeviceSeekPenaltyProperty`, тип шины) на томе файла, без прав; Linux — sysfs (есть, `FileDisk`) | `slow_disk`, оценка стриминга |
| Диск: скорость | чтение самого файла модели в обход кэша (`FILE_FLAG_NO_BUFFERING`, `O_DIRECT`, `F_NOCACHE`): последовательно блоками 4 МиБ с глубиной 4, до 1 ГиБ или 2 с; затем случайно блоками 64 КиБ, 1 с | формула стриминга (§3.2) |
| Питание: сеть/батарея, план, режим питания Windows | есть (`Power`); режим питания — `PowerGetEffectiveOverlayScheme`; Linux — `platform_profile`, governor | `on_battery`, `power_saver` |
| Загрузка: CPU за 1 с, GPU (загрузка, температура, частоты, причины троттлинга) | `GetSystemTimes`, `/proc/stat`; `nvidia-smi` | `busy_machine`, `hot_gpu`; температура простоя для замера |
| Контекст: ОС, VM, WSL, запущен ли процесс службой (сеанс 0) | есть (VM, WSL); сеанс — `ProcessIdToSessionId` | `session0_no_igpu` |
| Версии: nanollm, `libs.release`, коммит llama.cpp, сборка CUDA (12/13), модель и её sha256, драфтер | есть | ключ профиля, `cuda_addon_*` |

Чтение файла в обход кэша не требует прав. Поэтому скорость диска честная, даже если файл целиком лежит в
кэше ОС. Очистить кэш на Windows без прав администратора нельзя (AUTOTUNE.md, «Диск (Windows)»), и это
учитывается в §3.2.

### 3.2 Кандидаты и отсев

Кандидат — это устройство и бюджет. Планировщик превращает их в режим памяти (M1…M9), контекст и
LoadSpec, как сейчас. Новое в планировщике — **общий потолок** `Request.MemCap`: сумма private (RAM
закреплённая и анонимная, плюс накладные) и VRAM по плану не превышает потолка, файловые части не
считаются. С этим потолком планировщик на дискретной GPU сам уходит с M2 на M3, а если и так не
помещается — уменьшает контекст до минимума 4608 (§2).

Какие кандидаты строятся:

| Режим | Кандидаты |
| --- | --- |
| silent | CPU, бюджеты по возрастанию: ram-1g, ram-1.5g, ram-2g, ram-3g, ram-4g, ram-6g, ram-8g |
| optimal | дискретная GPU с `MemCap` 4 ГиБ (CUDA, если есть add-on, иначе Vulkan); iGPU uma-4g; CPU ram-4g |
| powerful | дискретная GPU с бюджетом из свободной VRAM; iGPU с бюджетом из свободной памяти; CPU с бюджетом из свободной RAM (`DerivedPreset`) |

**Отсев без запуска.**
- Не помещается в лимит памяти режима или в свободную сейчас память — отсеивается.
- Режимы, которые читают веса с диска на каждом токене (M8, M9), оцениваются формулой из AUTOTUNE.md:
  `tg ≈ скорость_диска / холодные_байты_на_токен`. Холодные байты берутся из плана (`stream_ranges`), скорость —
  из §3.1. При оценке ниже 1 ток/с кандидат отсеивается без замера. Например, на HDD с 130 МБ/с ram-2g даёт
  ~0,13 ток/с.
- Для тихого режима порог проверяется по **пессимистичной оценке**: модель не лежит в кэше, веса идут с
  диска. Если в RAM много свободного места, M9 на `ram-1g` реально работает из кэша и выглядит быстрым.
  Но человек, выбравший тихий режим, — как раз тот, у кого память занята, а кэш на Windows не очистить без
  прав. Поэтому решение не опирается на кэш, который может исчезнуть (решение владельца 2026-10-23).
- Очевидное превосходство измерять не нужно. Дискретная GPU с нашей `ggml-cuda.dll` против CPU (tg ~100
  против ~14 ток/с на rusunrisebook) — CPU не меряется. Правило: меряются все кандидаты, чья оценка времени
  типичного ответа (§3.4) не хуже лучшей больше чем в 1,5 раза, но не больше двух загрузок. Оценки pp и tg
  берутся из матрицы (§3.8): у каждого измеренного класса есть базовые скорости со ссылкой на файл замера, а
  незнакомый класс берёт ближайший. Когда опереться не на что, кандидат меряется.

### 3.3 Короткий замер

Замер идёт в отдельном рабочем процессе, как у `bench`: одна загрузка — один процесс. У процесса своя
пиковая память, а его падение — это провал кандидата, а не сервера. Во время замера резидентные экземпляры
модели выгружаются, так же как при `bench` из UI.

**Пробы на одной загрузке.** Чтобы уложиться в 2 минуты, рычаги, которые не требуют перезагрузки, меняются
на загруженной модели:
- потоки decode и prefill — `llama_set_n_threads`;
- `draft_max` и `p_min` драфтера MTP. Модель грузится с наибольшим `draft_max` из проб (`n_outputs` на
  последовательность задаётся при создании контекста), а в пробах значение понижается;
- MTP выключен — тот же прогон без драфтов.

Для этого в бэкенде нужны `SetThreads(n, nBatch)` и `SetDraft(max, pMin)`. На этапе 0 проверяется, что проба
на понижённом `draft_max` даёт те же цифры, что и загрузка с этим значением.

**Эталонный запрос.** Пробы повторяют типичный ответ из §3.4: промпт ~4096 токенов, потом ответ. Промпт —
встроенный текст на ~4000 токенов (свой, русский и английский, как тексты `bench`) и вопрос по нему в разметке
чата Gemma 4. Ответ получается пересказом по тексту, как в реальной работе. Повтор одной фразы (`ppText` у
`bench`) не годится: драфтер на нём угадывает почти всё и завышает пользу MTP. Текст и вопрос входят в версию
набора автонастройки, её хэш записывается в профиль.

**Ход пробы** на одной загрузке (по одному повтору, жадная выборка, конец генерации запрещён, как в `bench`):

1. Прогрев: 16 токенов decode на коротком промпте, не учитывается.
2. Prefill первых 512 токенов эталона. По этому времени считается прогноз для всех 4096.
3. Если прогноз ≤ 25 с, prefill всего промпта. Первые 512 токенов берутся из кэша промптов, считаются
   остальные, а время prefill — сумма шагов 2 и 3. Так замер честно включает рост цены внимания с глубиной.
   Если прогноз > 25 с (слабый CPU, 2 потока тихого режима), промпт остаётся длиной 512. Prefill и decode
   пересчитываются на глубину 4096 по коэффициентам класса устройства из AUTOTUNE.md (CPU: decode на 4096 —
   13,5 против 20,4 ток/с на пустом контексте; RTX: 98 против 104; Iris: prefill 331 против 475). В профиле
   такой результат помечен `extrapolated`.
4. Decode на этой глубине: 48 токенов ответа для каждого варианта MTP и без драфтов. Каждый вариант
   начинается с того же промпта из кэша, поэтому все варианты отвечают одинаково и их можно сравнивать.
   Доля принятых драфтов записывается.
5. Кандидаты со стримингом с диска (M8, M9): шаги 1–3, затем 8 токенов decode. Итоговая скорость —
   меньшее из замера и формулы диска из §3.2.

Какие варианты MTP пробуются (из AUTOTUNE.md):

| Устройство | Варианты |
| --- | --- |
| CPU с признаком `multirow-q4_0` | выкл.; 2 / p_min 0,5 (умолчание); 3 / 0 |
| CPU без признака | выкл.; 2 / 0,75 |
| CUDA | выкл.; 3 / 0 (умолчание); 2 / 0 |
| Vulkan (iGPU) | выкл.; 2 / 0 (на Iris Xe draft_max и p_min почти ничего не меняют) |
| CPU без признака или класс без замеров MTP | выкл.; лучший `draft_max` по пробе цены пачки (§3.8) |

Потоки на CPU меряются только на гибридном процессоре в производительном режиме: число P-ядер против всех
физических. В остальных случаях потоки задаёт правило режима.

**Нагрев.** Перед каждым кандидатом на GPU модуль ждёт, пока температура вернётся к простою + 3 °C, но не
дольше 30 с. Записываются температура, частоты и причины троттлинга на старте и в конце пробы. Если два
кандидата различаются меньше чем на 5 %, это ничья: решают вторичные признаки (§3.4).

**Память по замеру.** Рабочий процесс снимает пиковые значения во время проб:
- private: на Windows приватный рабочий набор (`PROCESS_MEMORY_COUNTERS_EX2.PrivateWorkingSetSize`, пик по
  выборке раз в 100 мс) плюс закреплённые страницы файла. `PeakWorkingSetSize`, который брал `bench`, включает
  страницы файла, а commit charge включает видеопамять под WDDM, поэтому ни то ни другое не годится. На
  Linux — пик `RssAnon + RssShmem` по выборке раз в 100 мс; на macOS — `phys_footprint`;
- VRAM процесса: на Windows счётчики PDH `\GPU Process Memory(pid_<pid>_*)\Dedicated Usage` и `Shared
  Usage`; на Linux для NVIDIA — NVML (память процесса). Если счётчика нет, сумма буферов llama.cpp
  (нынешний `PeakVRAM`) плюс контекст драйвера, найденный по разнице свободной памяти устройства до и после
  создания контекста. В профиле помечено, замер это или оценка;
- `Shared Usage` на дискретной GPU больше памяти хоста по плану (без 448 МиБ драйвера) на 256 МиБ означает, что
  драйвер выгрузил часть в общую память (случай vram-8g: pp 267, tg 65 вместо ~5000 и ~100). Такой кандидат
  отбрасывается, а модуль сообщает `vram_spill`. Просто «Shared > 0» не годится: в M2 закреплённая память хоста
  и есть Shared (2,04 ГиБ при плане 2,08), в M3 — 0,17 ГиБ при плане 0,22, в spill vram-8g — 0,68 при плане
  0,27 (+424 МиБ);

**Бюджет времени** (rusunrisebook: NVMe, RTX 3070 Ti Laptop, Iris Xe):

| Кандидат | Загрузка | Prefill 4K | Decode (варианты MTP) | Итого |

### 3.4 Выбор

**Типичный ответ** (решение владельца 2026-10-23). У каждого кандидата и варианта считается время ответа на
эталонную нагрузку: промпт 4096 токенов и ответ 300 токенов, `T = 4096 / pp₄ₖ + 300 / decode₄ₖ`. Здесь `pp₄ₖ` —
средняя скорость prefill всего промпта, `decode₄ₖ` — скорость ответа после него с лучшим вариантом MTP (§3.3).
Одно число соединяет prefill и decode и понятно человеку: «ответ на обычный вопрос: 4,1 с против 9,8 с».
Время загрузки сюда не входит, оно показывается отдельно.

| Режим | Правило |
| --- | --- |
| silent | наименьшая память, у которой decode ≥ 1 ток/с (по замеру и по пессимистичной оценке §3.2); при равной памяти — меньшее `T` |
| optimal | наименьшее `T` среди кандидатов, у которых и по плану, и по замеру ≤ 4 ГиБ + 200 МиБ |
| powerful | наименьшее `T` |

**Ничья** (разница меньше 5 %): берётся вариант с меньшей памятью, потом GPU раньше CPU (процессор
остаётся свободным), потом MTP выключен (меньше памяти на драфтер).

**Перепроверка памяти.** Если выбранный в оптимальном режиме кандидат по замеру превысил 4 ГиБ + 200 МиБ,
он отбрасывается и берётся следующий. Если не прошёл ни один, режим выполняется с наименьшим кандидатом, а
модуль сообщает `mode_degraded` с цифрами.

**Что выбирается и откуда.** У каждого рычага в профиле есть значение, источник (`measured`, `class`,
`inherited`, `mechanism`, `posture`, `rule`, `config`; §3.8), причина словами и, если мерили, цифры всех
вариантов.

| Рычаг | Источник в v1 | Основание |
| --- | --- | --- |
| устройство | замер или превосходство по оценке | §3.2 |
| бюджет, режим памяти, контекст и слоты | планировщик с ограничениями режима | `plan.Make`, `MemCap` |
| MTP: вкл./выкл., `draft_max`, `p_min` | замер | §3.3 |
| потоки decode / prefill | правило режима; замер на гибридном CPU в производительном | §2 |
| NUMA (`interleave` / `distribute`) | замер на машинах с несколькими узлами | AUTOTUNE.md, +23 % на EPYC |
| тип KV | f16; q8_0 только если f16 не даёт контекст 4096 в бюджете | AUTOTUNE.md, O2 и KLD |
| flash attention, сэмплинг на устройстве, repack, `cuda_nano` | правила по признакам устройства, как сейчас | AUTOTUNE.md |
| стример слоёв (`stream.*`), n-gram | выключены | на HDD вредит; на SSD не мерено (§8) |
| приоритет, EcoQoS | правило режима | §2 |

### 3.5 Проблемы

У каждой проблемы есть код, важность, понятный текст с цифрами и совет. Важность бывает трёх видов:
- `info` — к сведению;
- `warn` — снижает скорость или точность замера;
- `error` — режим недоступен в заявленном виде (модуль всё равно выбирает лучшее из возможного и говорит, что
  именно не выполнено).

### 3.6 Профиль

Профиль лежит в `<data_dir>/tune/<модель>.<режим>.json`; предыдущая версия сохраняется рядом как `.prev`.

**Ключ.** Если любая часть ключа меняется, профиль устаревает. Части ключа:
- режим;
- id модели, её sha256 и sha256 драфтера;
- `libs.release`, коммит llama.cpp и сборка CUDA;
- версия схемы профиля и набора проб (растёт, когда меняется логика выбора или эталонный запрос);
- выбранное устройство: класс, имя, объём памяти, версия драйвера;
- модель CPU, число ядер, объём RAM.

Свободная память в ключ не входит, потому что всё время меняется. Она записывается как условие замера.

**Содержимое:**
- ключ;
- дата и длительность;
- снимок осмотра;
- условия: питание, температура, загрузка;
- кандидаты с оценками и причинами отсева;
- замеры проб;
- выбранные рычаги с источником и причиной (§3.4);
- проблемы;
- проверка памяти: план и замер.

Набросок:

### 3.7 Применение

- **Конфиг.** Новая секция `tune.mode`: пусто — модуль выключен и поведение как сейчас; иначе `silent`,
  `optimal` или `powerful`. Модуль пишет её через `config/edit.go`: комментарии и порядок ключей
  сохраняются, как в `nanollm key`.
- **Порядок значений.** Явный ключ конфига (`models.overrides.<id>.*`, `devices.*`) > профиль > правило
  режима > статическое правило, как сейчас.
- **Режим без профиля.** Ограничения режима работают и без замера: `MemCap`, потоки, приоритет, устройства.
  Профиль только выбирает лучшее внутри них.
- **Устаревший профиль** (решение владельца 2026-10-23: предупредить и предложить перепроверить, самому не
  мерить). Сервер работает по ограничениям режима и статическим правилам и говорит, что изменилось и как
  перепроверить:
  - при старте — строка в логе: «профиль optimal устарел: драйвер 581.57 → 590.12; перепроверьте:
    `nanollm optimize`»;
  - `GET /api/v1/optimize` — `stale: true`, список изменений и предложение `{mode}` для повторного запуска;
  - `nanollm optimize` без `--mode` при устаревшем профиле сразу предлагает перепроверку в том же режиме
    (§4.1);
  - установщик при обновлении предлагает перепроверку (§4.3).

  Так же обрабатывается случай, когда `tune.mode` задан, а профиля для этой машины нет (конфиг перенесли на
  другую машину).
- **Приоритет и EcoQoS** тихого режима применяются при старте сервера ко всему процессу.
- **`nanollm plan`** показывает источник каждого значения: `config`, `profile`, `mode` или `rule`.
- **Отчёт `bench`** записывает хэш профиля (`Run.Plan` + поле `tune_profile`), чтобы результаты разных машин
  сравнивались вместе с их настройкой.

### 3.8 Матрица оптимизаций и неизвестное железо

**Принцип** (решение владельца 2026-10-23). Если на этом железе оптимизацию не мерили, это не причина её не
включать. Не включают её только в двух случаях: замер показал проигрыш (здесь или на близком железе) или есть
риск для правильности ответа. На современной машине, которой нет в матрице, модуль включает то, что по
ближайшим данным и по механизму должно ускорять, а короткий замер подтверждает это или откатывает. Худший
исход — сегодняшнее поведение без автонастройки, но не хуже.

**Матрица.** Файл `internal/tune/matrix.yaml` встроен в бинарь; начальное содержимое — приложение А. Одна запись
— одна ячейка:

```yaml
- lever: mtp
  variant: {draft_max: 2, p_min: 0.5}
  class: {cpu_variant: haswell}         # значимые признаки этого рычага (ниже)
  verdict: win                          # win | loss | neutral | depends
  effect: {metric: chat_tok_s, ratio: 1.38}
  conditions: {preset: ram-8g, threads: 16, numa: interleave}
  machines: [hyper]                     # на скольких машинах класса измерено
  source: bench/results/hyper/2026-10-20-dev-mtp-next2-strong.json
  why: "проверка 2–3 токенов стоит почти как один токен (ядра OPT-16)"
```

Тест проверяет, что файл-источник каждой ячейки существует (правило 2 из AUTOTUNE.md). AUTOTUNE.md остаётся
местом для фактов и объяснений, а матрица — его выжимка в машинной форме.

**Класс железа — набор признаков из осмотра, а не имя модели:**
- CPU: архитектура, вариант ggml CPU (`haswell`, `alderlake`, `zen4`…), ISA (AVX2, AVX-VNNI, AVX-512, dotprod,
  i8mm), гибрид P/E, число узлов NUMA;
- GPU: бэкенд (CUDA, Vulkan), производитель, своя или общая память, compute capability, признаки устройства;
- диск: тип и скорость.

**Значимые признаки у каждого рычага свои.** Ближайшая ячейка ищется только по ним, поэтому новая модель
процессора или карты не делает рычаг «неизвестным», если значимые признаки совпали.

| Рычаг | Значимые признаки |
| --- | --- |
| repack, многострочные ядра Q4_0 | вариант ggml CPU (какие ядра собраны) |
| MTP, n-gram | цена проверки пачки на этом устройстве (механизм, ниже); доля принятых драфтов — свойство модели и текста |
| потоки decode / prefill | гибрид P/E, упор decode в память |
| NUMA | число узлов |
| сэмплинг на устройстве | бэкенд × своя или общая память |
| FA `small` | бэкенд × своя или общая память |
| формы MMVQ (`cuda_nano`) | compute capability |
| большой mat-vec Vulkan (патч 0006) | производитель × общая память × ОС |
| n_ubatch | бэкенд |
| KV q8_0 | не наследуется (правило памяти) |
| стриминг, M8/M9 | диск (формула §3.2) |

**Откуда берётся значение**, по убыванию силы:
1. `measured` — замер на этой машине;
2. `class` — ячейка с теми же значимыми признаками;
3. `inherited` — ближайшая ячейка. Процессор с надмножеством ISA ближе к классу с AVX2, чем к «x86 вообще»;
   соседняя compute capability ближе дальней; тот же бэкенд и тип памяти важнее производителя;
4. `mechanism` — проба механизма на 1–3 с (ниже);
5. `posture` — правило по типу рычага (следующая таблица).

Так у каждого рычага на любой машине есть значение, а в профиле видно, откуда оно взялось.

**Тип рычага решает, как использовать унаследованное:**

| Тип | Что меняется | Примеры | Выигрыш у ближайшего | Проигрыш у ближайшего | Данных нет |
| --- | --- | --- | --- | --- | --- |
| Точный | только скорость, вывод тот же | repack, граф на форму, кэш q8_1, потоки, NUMA, n_ubatch, MTP, сэмплинг на устройстве | включить | выключить; пробовать, если есть время | проба механизма; без неё — умолчание сборки |
| Форма ядра | порядок суммирования, вывод в пределах шума ядер | формы MMVQ, `FA_VEC`, FA `small` | кандидат против upstream: решает проба и проверка правильности | upstream | upstream |
| С ценой качества | ответ может измениться заметнее шума | KV q8_0 | не наследуется: только когда без него не помещается минимальный контекст | — | — |
| От диска | скорость задаёт диск, а не процессор | M8/M9, опережающее чтение, вытеснение | не наследуется: формула и замер | — | — |

Многое неизвестная машина получает и без автонастройки. Наша `ggml-cuda.dll` включает на любой карте NVIDIA
пять из семи своих правок: граф на форму батча, кэш q8_1, норму с q8_1, лёгкую норму и `gelu·mul`. Только
форма блока MMVQ стоит в таблице для cc 8.6; на другой карте её пробует модуль.

**Пробы механизма** (на той же загрузке, 1–3 с каждая):
- **Цена пачки → MTP.** Время прохода 1, 3 и 4 токенов на текущей глубине, `c(k) = t(k) / t(1)`. Доля принятых
  драфтов `a` при жадной выборке — свойство модели и текста, на любом устройстве почти одна. Её таблица по
  позициям драфта берётся из наших замеров. Ожидаемое ускорение `E(k) = (1 + a₁ + a₁a₂ + … ) / (c(k+1) + k·d)`,
  где `d` — цена шага драфтера (≈1 % прохода цели на CUDA, единицы процентов на CPU). Проба подтверждает лучшее
  `k` против «выкл.». Так MTP решается на процессоре, для которого у нас нет ядер (AVX-512, ARM): сегодня
  статическое правило выключает там MTP только потому, что нет признака `multirow-q4_0`. Цена пачки на
  hyper, `scripts/tn-curve.sh`: 1,01× и 1,11× для 2 и 3 токенов; там MTP выигрывает.
- **Копия логитов → сэмплинг на устройстве.** Время копирования строки логитов (1 МиБ) на хост плюс цепочка на
  хосте против цепочки в графе устройства. Решает сэмплинг на незнакомом бэкенде или карте.
- **Узлы NUMA > 1** → `interleave` и `distribute` оба идут в пробу.

**Общая проверка.** На классе без своих ячеек модуль после выбора делает одну пробу: «всё выбранное» против «без
автонастройки», то есть статических правил, по которым сервер работает сегодня. Если выбранное медленнее
больше чем на 5 %, по одному откатываются рычаги с источником `inherited` и `mechanism`, начиная с наименее
уверенного, пока не найдётся виновник.

**Проверка правильности.** Короткий промпт (~64 токена) и 32 токена ответа с MTP и без него должны совпасть
токен в токен. На коротком контексте шум split-KV не проявляется: AUTOTUNE.md, «Точность проверки пачкой».
Это та же проверка, что `TestNativeMTPEquivalence`, только на машине пользователя. Ответы, разошедшиеся в
«почти ничьей» (на обычном прогоне видны альтернативы токена: токен драфтового прогона среди пяти лучших
обычного, и их логарифмы вероятностей различаются не больше чем на 0,1), считаются совпавшими: пачка проверки
и пачка из одного токена могут считаться разными ядрами (CUDA суммирует в другом порядке), и где модель выбирает
между двумя словами, жадный выбор может уйти в любую сторону. В профиле это `draft_near_tie`. Строгое равенство
дало бы ложную тревогу и выключило MTP, который даёт ×1,9. Если ответы не совпали сильнее:
1. кандидаты формы ядра откатываются к upstream, проверка повторяется;
2. если не помогло, MTP на этом устройстве выключается, и выводится проблема `draft_mismatch` (warn) с
   предложением прислать профиль.

Форма блока MMVQ для одного токена и для 2–4 токенов (`MMVQ_NWARPS` и `MMVQ_NWARPS_N`) должна быть из одной
семьи по числу варпов: при рассогласовании проверка пачкой перестаёт воспроизводить обычный decode (замер этапа
0: разрыв до 0,19 нат). Кандидаты формы будущего `optimize --deep` меняют обе величины вместе.

**Порядок проб при нехватке времени.** Пробы идут по произведению «ожидаемый выигрыш × неуверенность». Первым
меряется то, что на близком классе давало много, а здесь не мерено: MTP, форма MMVQ. Если время кончилось,
непроверенные рычаги остаются на унаследованных значениях, а не выключаются. В отчёте они помечены «не
подтверждено».

**Отчёт говорит, откуда что.** Пример: «применено 11 рычагов: 4 измерено здесь, 5 по аналогии с Iris Xe (Intel,
общая память, Windows), 2 по механизму; общая проверка: +38 % к работе без автонастройки».

**Примеры машин, которых нет в матрице:**

| Машина | Что получает |
| --- | --- |
| Intel Core Ultra 7 155H (Meteor Lake: AVX-VNNI, гибрид; iGPU Arc Xe-LPG) | CPU: класс `alderlake` (тот же вариант ggml и ядра патча 0005), всё как на 12700H. iGPU: по аналогии с Iris Xe (Intel, общая память, Windows) — FA `small`, патч 0006, MTP, сэмплинг на хосте; общая проверка подтверждает |
| AMD Ryzen 7 7840HS (Zen 4: AVX-512 и AVX512-VNNI; iGPU Radeon 780M) | CPU: вариант `zen4`, ядер 0002/0005 нет, признака `multirow-q4_0` нет. MTP решает проба цены пачки, а не правило «выкл.»; repack — ядра upstream. iGPU: Vulkan с общей памятью, не Intel. Сэмплинг на хосте и FA по аналогии с Iris; FA `small` — кандидат (включается ключом `flash_attention: small`); патч 0006 — кандидат, когда у него будет выключатель (сейчас он включается только для Intel) |
| NVIDIA RTX 4070 Laptop (cc 8.9) | Пять правок нашей DLL включены сразу. Форма MMVQ: кандидат «как у 8.6» против upstream, с проверкой правильности. FA одного токена с Ada и так векторный. MTP 3 / 0 по аналогии с RTX 3070 Ti и проба; сэмплинг на устройстве; сборка CUDA 13 при драйвере 580+ |

## 4. Интерфейсы

### 4.1 `nanollm optimize` (TUI и CLI)

```
nanollm optimize [--mode silent|optimal|powerful] [--yes] [--dry-run] [--json] [--model ID] [-config FILE]
```

**Где идёт замер.** Если служба по адресу из конфига отвечает, команда работает как клиент HTTP API с
admin-ключом из конфига. Тогда замер идёт внутри службы: та же учётная запись и те же устройства, что в
работе. Если службы нет, команда запускает рабочие процессы сама и сама пишет профиль и конфиг.

**Интерактивный ход (TTY):**
1. осмотр: что найдено и проблемы;
2. выбор режима стрелками. У каждого режима одна строка с цифрами этой машины, например «до 4 ГиБ, 7 потоков,
   ожидается ~100 ток/с на GPU»;
3. прогресс: этап, кандидат, проба, оставшееся время;
4. итог: что выбрано и почему, таблица кандидатов, проблемы;
5. «Применить? [Y/n]».

**Устаревший профиль.** Если режим уже задан, а профиль устарел или его нет, команда без `--mode` начинает с
предложения: «Профиль optimal устарел (драйвер 581.57 → 590.12). Перепроверить в том же режиме? [Y/n]». Ответ
«нет» ведёт к обычному выбору режима.

**Без TTY и с `--yes`:** обычные строки, без вопросов. `--json` выдаёт итог в формате профиля.

**Реализация:** своя на `golang.org/x/term` (сырой режим клавиатуры; модуль команды Go, x/sys у нас уже
есть). Фреймворк TUI не берём: у бинаря сейчас четыре прямые зависимости.

Набросок итога:

```
NanoLLM optimize — optimal (≤ 4 GiB, ≤ 7 threads)

  chosen   CUDA (RTX 3070 Ti Laptop), vram-ple-disk, 8k context, MTP 3
           typical answer 2.5 s: 4096-token prompt at 5600 tok/s, 300 tokens at 167 tok/s
  memory   3.9 GiB planned, 3.8 GiB measured (limit 4.0 + 0.2)

  candidate              memory   prefill   decode   answer   verdict
  cuda0 vram-ple-disk    3.8 GiB     5600      167    2.5 s   chosen
  cpu ram-4g             3.5 GiB        —        —  ~40 s     not measured: estimate ×16 slower
  vulkan0 uma-4g         3.6 GiB        —        —  ~32 s     not measured: estimate ×13 slower

  ! vram_busy   other programs hold 3.2 GiB of VRAM (chrome.exe, steam.exe)
  i cuda13      driver 581.57 runs the CUDA 13 build

Apply? [Y/n]
```

(Числа в наброске для формы; настоящие покажет этап 0.)

### 4.2 HTTP API

Все маршруты только для admin-ключа, тот же стиль, что у `bench`:

| Маршрут | Что делает |
| --- | --- |
| `POST /api/v1/optimize {mode, model?, dry_run?}` | 202 `{id, estimate_s}`. `mode` — только `silent`, `optimal`, `powerful`, иначе 400. Второй запуск при идущем — 409 |
| `GET /api/v1/optimize/{id}/events` | SSE: `survey`, `problem`, `candidate`, `probe`, `decision`, `done`, `error` |
| `GET /api/v1/optimize/{id}` | состояние и результат (JSON профиля) |
| `POST /api/v1/optimize/{id}/apply` | делает профиль активным, пишет `tune.mode` в конфиг, перезагружает модель по новому плану |
| `GET /api/v1/optimize` | текущий режим, сводка активного профиля, флаг `stale`, проблемы |

Во время замера сервер ведёт себя как во время `bench` из UI: резидентные экземпляры модели выгружены,
запросы к модели получают 503 с `Retry-After`, задачи очереди ждут.

### 4.3 Установщики

`install.ps1`: новые параметры `-Mode silent|optimal|powerful` и `-NoOptimize`. `install.sh`: `--mode` и
`--no-optimize`.

Порядок шагов:
1. `init` и загрузка модели (как сейчас);
2. регистрация и старт службы, проверка `/healthz`;
3. `nanollm optimize --config <cfg> --mode <M> --yes` — как клиент API службы, замер внутри службы.

Без `-Mode` в интерактивной консоли установщик показывает три строки с описанием режимов (по умолчанию
оптимальный). При запуске через `irm … | iex` (без консоли) выбирается оптимальный без вопроса. Если модель
не скачана (`-NoDownload`) или замер не удался, установщик пишет предупреждение и команду для повтора, а
служба работает на ограничениях режима и статических правилах.

**Обновление.** Установщик не трогает конфиг, но новые библиотеки (`libs.release`) или драйвер делают
профиль устаревшим. Тогда установщик предлагает перепроверку в том же режиме:
- в интерактивной консоли — вопрос (по умолчанию «да»);
- с `-Mode` — перепроверяет без вопроса;
- без консоли и без `-Mode` — пишет предупреждение и команду `nanollm optimize`.

Сам установщик по-прежнему повышает права для своих шагов (Program Files, служба, PATH). Модулю права не
нужны: он работает внутри службы.

## 6. Порядок работ

0. **Замеры, без которых правила не на чем строить** (rusunrisebook):
   - M3 (vram-ple-disk) против M2 на CUDA: скорость, private, VRAM вместе с контекстом драйвера.
     Помещается ли в 4 ГиБ + 200 МиБ и при каком контексте;
   - счётчики PDH `GPU Process Memory` от обычного пользователя и от LocalSystem: доступны ли и совпадают ли
     с буферами llama.cpp плюс контекст;
   - `PeakPagefileUsage` против плана для ram-4g, uma-4g и M3;
   - пробы на одной загрузке: `SetDraft` на понижённом `draft_max` и `SetThreads` дают те же числа, что
     отдельная загрузка;
   - тихий режим: 2 потока, ram-1g…ram-4g на NVMe по формуле и по замеру, decode после промпта 4096; где
     проходит порог 1 ток/с;
   - эталонный текст на ~4000 токенов и вопрос к нему; коэффициенты пересчёта с 512 на 4096 для CPU, Iris и
     RTX (§3.3, шаг 3), проверка расхождения (§7);
   - можно ли менять `cuda_nano` (форму MMVQ) на загруженной модели через `ggml_backend_cuda_nano_set`. Если нет,
     кандидат формы стоит ещё одной загрузки (на GPU 3–8 с);
   - проба цены пачки против полного свипа MTP на CPU (EPYC, 12700H), Iris и RTX: совпадает ли лучшее `k`;
   - выключатель для патча 0006 (переменная окружения), чтобы он мог быть кандидатом на iGPU не Intel.

   **Итоги этапа 0** (rusunrisebook, 2026-10-23, `bench/results/rusunrisebook/optimize-stage0-2026-10-23/`):
   - M3 на CUDA не медленнее M2 (+3 % pp, +6 % tg, MTP в пределах 1 %) и при контексте 8192 держит
     4,02 ГиБ: оптимальный режим на RTX помещается. Правило порядка режимов под лимитом включено (M2 пропускается);
   - процесс с контекстом CUDA или Vulkan держит ~448 МиБ приватной памяти сверх плана (CUDA: 695 МиБ при
     плане 223; Iris Xe через Vulkan: 3,65 ГиБ при плане 3,21). План CPU совпадает с замером в пределах 1 %;
   - PDH `GPU Process Memory` доступны обычному пользователю; от LocalSystem не проверено (нужна служба,
     то есть права администратора для установки). Правило `vram_spill` — Shared больше памяти хоста по плану
     на 256 МиБ (M2 −47 МиБ, M3 −47 МиБ, vram-8g +424 МиБ);
   - пробы на одной загрузке (`SetDraft` ниже загрузочного, `SetThreads`, `TimeBatch`) дают те же числа, что
     отдельная загрузка (нативный `TestNativeTunerEquivalence`);
   - тихий режим на NVMe: ram-1g (0,6 ГиБ private) держит 2,7 ток/с, поэтому он и выбирается; два потока
     декодируют так же быстро, как шесть (11,25 против 11,1 ток/с), приоритет ниже обычного с EcoQoS скорости
     не стоит. Формула диска для стриминга — нижняя граница (1,5 ток/с против измеренных 2,7);
   - коэффициенты глубины 4096: CPU 0,86 / 0,87, Iris 0,92 / 0,80, RTX 1,12 / 0,96 (prefill / decode); для
     одного CPU они расходятся до 9 % между числами потоков, поэтому хранятся в базовых скоростях класса, а
     полный промпт мерится, когда прогноз ≤ 25 с;
   - смена формы MMVQ на загруженной модели после захвата графов CUDA не действует: кандидат формы стоит
     загрузки (`TestNativeCudaNanoAtRuntime`);
   - цена пачки выбирает лучшее `draft_max` точно на обеих GPU, в пределах 2 % на двух прогонах CPU и в пределах
     10 % на третьем;
   - `CUDA_VISIBLE_DEVICES=-1` зависает на перечислении устройств с библиотеками релиза: проблему
     `cuda_addon_missing` воспроизводят каталогом библиотек без add-on (§7);
   - выключатель патча 0006 требует релиза библиотек, v1 его не ждёт (§8).

## 7. Проверка

- **Время.** Каждый режим на rusunrisebook укладывается в 2 минуты от начала до итога.
- **Оптимальный.** Замер выбранной конфигурации ≤ 4 ГиБ + 200 МиБ (private + VRAM); потоков ≤ 7 на
  i7-12700H; на RTX выбрана CUDA.
- **Тихий.** CPU, 2 потока, приоритет ниже обычного; decode ≥ 1 ток/с. На hyper (HDD) выбран не стриминг, а
  ram-3g или ram-4g.
- **Производительный.** На RTX — CUDA с бюджетом из свободной VRAM, без `vram_spill`, MTP 3 / 0.
- **Проблемы.** Каждая воспроизводится вручную: питание от батареи, план «экономия», add-on CUDA удалён
  (нет `ggml-cuda.dll`), VRAM занята, модель на HDD (D: или hyper).
- **Без прав.** Весь ход от обычного пользователя без повышения. Через API — внутри службы от LocalSystem.
- **Модульные тесты** логики выбора на синтетических осмотрах из фактов AUTOTUNE.md: hyper в сильном и слабом
  профилях, rusunrisebook CPU, Iris и RTX. Ожидаемый выбор и тексты причин — как golden.
- **Слепой прогон (неизвестное железо).** Из матрицы убираются ячейки классов самой машины: на
  rusunrisebook — `alderlake`, Iris Xe, cc 8.6; на hyper — `haswell` и NUMA. Модуль должен набрать не меньше
  95 % скорости типичного ответа, которую он получает с полной матрицей, и ни одной проблемы `draft_mismatch`.
  Так проверяется, что без замеров на классе оптимизации не теряются.
- **Эталонный запрос.** На CPU 12700H с 7 потоками полный prefill 4096 и пересчёт с 512 (§3.3, шаг 3)
  расходятся по `T` не больше чем на 10 %. Иначе коэффициенты пересчёта уточняются.
- **Устаревание.** Смена `libs.release` или драйвера в ключе делает профиль устаревшим. Сервер работает по
  правилам, пишет, что изменилось, и предлагает перепроверку: в логе, в API, в `nanollm optimize` и в
  установщике при обновлении.
- **API.** Бэкенд `fake` проходит весь путь: SSE, `apply`, перезагрузку модели.

## 8. Вне рамок v1

- **Глубокая настройка ядер:** формы MMVQ для новых compute capability, `FA_VEC` и прочие `cuda_nano`,
  тайлы Vulkan. Переключатель после захвата графов CUDA не действует, поэтому каждая форма стоит загрузки
  (3–8 с); займёт минуты на карту; потом `optimize --deep`.
- **Выключатель патча 0006** (переменная окружения): нужен релиз библиотек.
- **Рычаги без замера:** n-gram, KV q8_0 (нужен гейт качества), стример слоёв `ahead`/`keep` на SSD,
  `distribute` под нагрузкой сервера.
- **Устройства:** NPU и Metal.
- **Экран в веб-UI:** API для него готов.
- **Фоновый перезамер** при устаревшем профиле: владелец решил, что сервер только предупреждает и
  предлагает (§3.7).

## 9. Решения владельца (2026-10-23)

1. Потребление памяти — private bytes процесса + VRAM процесса, без страничного кэша файла модели (§2.1).
2. Порог работоспособности — 1 ток/с; медленнее вариант не выбирается ни в одном режиме (§2).
3. Порог тихого режима проверяется по пессимистичной оценке: модель не в кэше, веса идут с диска (§3.2).
4. «Половина ядер» оптимального режима — половина физических ядер, P и E вместе (§2).
5. Тихий режим — только CPU, 2 потока, приоритет ниже обычного (§2).
6. Бенчмарк — до ~2 минут на типичном ноутбуке (§3.3).
7. Типичный ответ — промпт 4096 токенов и ответ 300 (§3.4); отсюда минимальный контекст 4608 (§2).
8. Производительный режим при свободной памяти меньше 6 ГиБ — лимиты памяти оптимального, все ядра,
   сообщение `mode_degraded` (§2).
9. Результат — профиль в `<data_dir>/tune/` и строка `tune.mode` в конфиге (§3.6, §3.7).
10. Устаревший профиль — предупредить и предложить перепроверку, самому не мерить (§3.7).
11. Установщик запускает замер через API службы (§4.3).
12. HTTP API принимает только три режима (§4.2).
13. Режима без замера (`init --mode`) нет: настройки всегда подбираются замером на конкретной машине. Для
    образов и CI `nanollm optimize` запускается на целевой машине: установщиком или вручную после первого
    старта.
14. Оптимизацию не выключают только потому, что её не мерили на этом железе. Значение берётся у ближайшего
    класса по значимым признакам рычага или из пробы механизма, а короткий замер подтверждает (§3.8). Матрица
    известных оптимизаций по классам железа — приложение А.

Сам решил без вопроса (можно оспорить):
- TUI на `golang.org/x/term` без фреймворка (§4.1);
- `bench` только записывает хэш профиля в результат и не меняет свои пресеты: публичный набор должен
  оставаться сравнимым;
- явный `device` в запросе выполняется и в тихом режиме: порядок «конфиг > профиль > режим > правило» один для всех;
- тихий режим без профиля берёт бюджет min(ram-4g, `DerivedPreset`);
- установка, где режим ещё не задан, обновляется как «профиля нет»: установщик предлагает настройку;
- по итогам этапа 0: под лимитом памяти M2 пропускается (M3 не медленнее и держит меньше памяти хоста); к плану
  прибавляются 448 МиБ памяти драйвера CUDA или Vulkan (§2.1); `vram_spill` — Shared больше памяти хоста по
  плану на 256 МиБ (§3.3); формы ядер CUDA в v1 не пробуются, потому что стоят загрузки (§8).
