# NanoLLM — роудмап разработки

**Decent LLM for any device.** Задача проекта: приличная LLM на любом
устройстве. Один и тот же NanoLLM должен давать пригодную модель на машине с
GPU, на ноутбуке со встроенной графикой и на машине только с CPU и малым
объёмом RAM; пресеты и планировщик подбирают размещение под железо.

Роудмап раскладывает вехи спецификации (v0.1 → v1.0 → v2.0 → v3.0 и
оптимизационные стадии O1–O5, SPEC §14) по четырём средам, в которых идёт
разработка. Номера `§N` ссылаются на NanoLLM Development Specification.

Правило одно: **этап закрывается только тем, что на его железе можно
доказать.** Всё, что не зависит от скорости и от конкретного ускорителя,
делается раньше, чем появится нужная машина. Всё, что зависит, начинается за
интерфейсом с подделкой и доказывается позже на реальном железе.

## Решения, принятые после спецификации

Эти решения сужают спецификацию. Где они расходятся, роудмап следует им.

| Решение | Что меняется относительно спеки |
| --- | --- |
| Только int4. Неквантованные варианты не рассматриваются вообще | Нет BF16/F16-эталонов, нет Q8_0. Гейт качества §13 «против BF16» заменяется гейтом против того же int4 в самой точной конфигурации рантайма (см. «Гейт качества») |
| Одна модель: Gemma 4 E4B QAT int4 от Unsloth (`UD-Q4_K_XL`) + MTP-драфтер Unsloth | Gemma 4 12B и Qwen3.5-9B отложены. Нет выбора варианта в O1 (Google `Q4_0` не сравнивается), нет снапшотов DeltaNet, нет fallback на Q8_0 |
| Metal появится только на финальных тестах | Гейт v0.1 закрывается на CPU, Vulkan и CUDA. Metal проверяется перед релизом v1.0 (этап 4) |
| NPU: AMD и Intel проверяемы, Qualcomm — нет | Кандидаты гейта v2.0 — VitisAI (Ryzen AI) и OpenVINO (Intel). QNN и Windows ARM64 не проверяются |
| Тестовый ноутбук: Windows и WSL2 (Ubuntu) | Linux на целевом железе — только через WSL2, со всеми его отличиями (см. этап 3) |
| Слепую оценку людьми делает один человек | Небольшие наборы: 50 промптов на базовую приёмку, 20–30 пар на регрессию, и только когда автоматика что-то заметила |
| Публичный бенчмарк: `nanollm bench` прогоняет пресеты на эталонных промптах, результаты по явному согласию уходят на nano.llmto.day (страница Benchmarks). Код клиента и сервиса — в этом репозитории, сервис потом выносится | Отступление от §1 «сеть нужна только для весов»: вторая сетевая функция, только opt-in, без телеметрии. Дизайн — [BENCHMARKS.md](BENCHMARKS.md) |

## Карта этапов

| Этап | Среда | Что закрывает |
| --- | --- | --- |
| 1 | Текущая VM: 4 vCPU, 15 GB RAM, ~25 GB диска, без GPU | Весь код v0.1 и v1.0, которому не нужна скорость: биндинг, GGUF-инвентарь, планировщик, сервер целиком на фейковом бэкенде, реестр, UI, сборка и инсталляторы. Инструменты для оценки качества. Клиент и сервис бенчмарка |
| 2 | AMD EPYC 7351P, 128 GB RAM, без GPU | CPU-часть гейта v0.1, режимы M6–M9 и пресеты `ram-*`, эталон качества и первая оценка, O2 для RAM-пресетов, нагрузка на сервер |
| 3 | Core i7-12700H, RTX 3070 Ti Laptop 8 GB, 32 GB RAM, Windows + WSL2 — целевая среда | CUDA/Vulkan-часть гейта v0.1, доказательство M2 (PLE в RAM) на реальном GPU, пресеты `vram-*` и комбинированные, O2 для GPU, O3 (MTP), Windows целиком, кандидат v1.0 |
| 4 | Mac, Ryzen AI, Intel, Core i5-1035G | Metal и `uma-*`, подпись macOS, релиз v1.0 на пяти платформах, v2.0 (NPU: VitisAI и OpenVINO), решение по v3.0 (MLX), нижняя граница железа |

Что из этой карты стоит держать в голове:

- **Metal проверяется последним.** Metal-путь отличается от остальных:
  unified memory, M3 без копирования, `iogpu.wired_limit_mb`. Его ошибки
  обнаружатся поздно. Снижение риска — CPU smoke на macOS в GitHub CI с
  этапа 1 и unit-тесты учёта UMA-бюджетов в планировщике.
- **Гейт v2.0 держится на двух вендорах NPU, AMD и Intel.** У AMD условие в
  том, что onnxruntime-genai со сборкой VitisAI берётся у AMD (в публичных
  сборках её нет). У обоих общий риск §3: E4B может не экспортироваться в
  ORT GenAI. Тогда NPU откладывается, модель не меняется.

## Сквозные принципы

- **Фейковый бэкенд.** `internal/backend/fake` реализует `backend.Model`:
  токенизатор по байтам и детерминированные логиты по сценарию. Он даёт
  разработать и прогнать под `-race` весь сервер на этапе 1: пул, слоты,
  continuous batching, prompt cache, очередь, диалекты и UI. Реальный бэкенд
  подключается под те же тесты.
- **Golden-тесты — это данные.** Эталонные токены от `llama-cli` того же
  закреплённого тега лежат в `testdata/golden/<tag>/`. Любая машина прогоняет
  их и пишет результат в `verified[]` манифеста.
- **Бенчмарки с профилем машины.** JSON из `nanollm bench` хранится в
  `bench/results/<machine>/` вместе с CPU, памятью, диском, ОС и драйверами.
  Цифры одной машины никогда не переносятся на другую. Тот же формат
  (`nanollm.bench/v1`) уходит в публичный бенчмарк, если пользователь
  согласен (см. [BENCHMARKS.md](BENCHMARKS.md)).
- **Каждая новая машина становится self-hosted раннером CI.** Это нужно, чтобы
  обновление llama.cpp прогоняло golden-тесты везде, где они уже проходили.

## Гейт качества

Неквантованного эталона нет, поэтому вопрос «насколько int4 хуже BF16» не
задаётся. Задаются два других:

1. **Достаточно ли E4B int4 хорош как модель по умолчанию.** Это абсолютная
   оценка:
   - автоматические метрики на русском и английском: следование инструкциям,
     валидность JSON (по построению 100 % через грамматику), точность tool
     calls; всё с thinking и без;
   - одна слепая оценка человеком: 50 русских промптов, оценка 1–5 и пометка
     «годится / нет». Это примерно час работы, один раз на этапе 2.
2. **Не портит ли рантайм модель.** Это относительная оценка. Эталон — тот же
   `UD-Q4_K_XL` в самой точной конфигурации: CPU, KV f16, без MTP, закреплённый
   тег llama.cpp. С ним сравнивается всё остальное — CUDA, Vulkan, KV q8_0,
   каждый пресет и режим, каждое обновление тега. Метрики: KLD (среднее и
   p99) и top-1 agreement по `llama-perplexity --kl-divergence` на ru/en
   корпусе.
   - Порог KLD и top-1 калибруется после первого прогона: CPU против CUDA
     задаёт уровень «нормального шума» между бэкендами.
   - Если конфигурация выходит за порог или падают задачи, нужно слепое
     сравнение человеком: 20–30 пар против эталонной конфигурации.
   - Гейт по-прежнему применяется к каждой способности отдельно (ru
     инструкции, JSON, tools, thinking, длинный контекст). Средние значения
     в отчёте есть, но решение по ним не принимается.

## Этап 1 — текущая VM: разработка без полноценного инференса

**Что есть.** 4 vCPU, 15 GB RAM, около 25 GB свободного диска, без GPU. Проверено:
Hugging Face доступен (API репозиториев, загрузки, range-запросы), `git`
к llama.cpp работает, релизные архивы llama.cpp с github.com скачиваются.
GitHub API для чужих репозиториев закрыт прокси сессии, поэтому всё, что
требует API (проверка релизов), идёт через GitHub Actions.

Это значит, что этап не «без инференса», а **без инференса, по которому можно
судить**. `libllama` берётся из релизных архивов закреплённого тега, сборка
из исходников остаётся запасным вариантом. Крошечные модели и сам E4B
запускаются для smoke-тестов (единицы токенов в секунду). Выводы о скорости
и качестве здесь не делаются.

**Подробный план этапа** — задачи, порядок, контрольные точки и факты
закреплённого тега, которые его определяют, — в [STAGE1.md](STAGE1.md).
Ниже — сводка.

### 1.1 Закрепление зависимостей — сделано

Итог: тег `b11600` (2026-10-13), `libs.sha256` заполнен по дайджестам самого
релиза, workflow `libs` проверяет все цели и оба CUDA add-on. Каталог
закреплён на коммит `8c5a9e4` репозитория Unsloth; драфтер — корневой
`mtp-gemma-4-E4B-it.gguf`, «smart Q4_0» (int4).

- Выбрать тег llama.cpp ≥ `b9568`, записать в `scripts/llama.cpp.tag`.
- Сверить имена архивов в `fetch-libs.sh` с реальным релизом и записать
  `scripts/libs.sha256`. Дальше `fetch-libs` проверяется в CI на каждом
  пуше.
- Каталог: оставить одну модель, `gemma-4-e4b-qat`. Записи 12B и Qwen3.5
  убрать до возвращения к ним.
- Закрепить её коммит репозитория, размеры и SHA-256 обоих файлов через HF API
  (LFS-метаданные дают sha256 без скачивания).

### 1.2 Реестр

- Загрузчик: докачка, проверка SHA-256 до использования, зеркала
  (`registry.mirrors`), `strict_license`.
- `models pull / list / rm`. `init` скачивает E4B вместе с драфтером.
- `POST /api/v1/models/{id}/download` с прогрессом по SSE.

### 1.3 GGUF-инвентарь

- Парсер заголовка GGUF на Go: метаданные, chat template, тензоры со
  смещениями.
- Классификатор групп G0–G7 по именам тензоров `gemma4` и `gemma4-assistant`.
- `models inspect --tensors` строит инвентарь. Он хранится в
  `internal/registry/tensors/<id>.json` с привязкой к sha256 файла и
  подгружается в `tensors[]` манифеста, чтобы не раздувать каталог.
- **Это первый ответ на главный открытый вопрос §4:** сколько байт в E4B
  занимает PLE, а сколько ядро. Для ответа нужен только заголовок файла.
  Провизорная карта пресетов (§15) пересчитывается сразу, а не после O1.

### 1.4 Планировщик

- Учёт байт по инвентарю. KV по точной формуле закреплённого тега: `n_ctx`
  и `n_ctx_seq` выравниваются до 256, SWA-слои держат
  `pad256(min(n_ctx_seq, n_swa·(unified ? n_seq_max : 1) + n_ubatch))`
  ячеек, full-слои — `n_ctx_seq`; KV есть у `block_count − shared_kv_layers`
  слоёв (у E4B — SWA 512, общий KV на 18 из 42 слоёв). Квантованный V
  требует FA. Формула сверяется с логом libllama (см. [STAGE1.md](STAGE1.md)).
- **`swa_full`.** Если полный SWA-кэш помещается в бюджет, план ставит
  `swa_full=true`, и prompt cache переиспользует префикс любой длины. Иначе
  `swa_full=false`, переиспользование только в пределах окна, а план пишет
  причину.
- Оценка compute-буферов, которая калибруется на этапах 2–3. Вторая копия
  tied `token_embd` в VRAM, если выходной слой на GPU.
- Порядок M1 → M2 → M3 → M4 → M6 → M7 → M8 → M9, пол `n_ctx = 4096`, один
  слот, отказ с недостачей в байтах.
- `nanollm plan gemma-4-e4b-qat --preset <name>`. Табличные тесты на все 19
  пресетов, включая `uma-*`: Metal появится поздно, поэтому учёт unified
  memory проверяется хотя бы арифметикой.

### 1.5 Биндинг к libllama

- **Спайк ABI первым делом:** purego v0.11.2 передаёт структуры по
  значению, поэтому C-шим не нужен. Это проверяется в CI на шести целях;
  план Б — шим, собранный `zig cc`.
- Генератор биндинга по `llama.h` закреплённого тега (`tools/bindgen`), с
  проверкой раскладки структур через `_Static_assert` для всех целей.
  `llama_build_number` в этом теге нет: при старте `ggml_commit()` сверяется
  с закреплённым коммитом, несовпадение — понятная ошибка.
- `ggml_backend_load_all_from_path(<lib>)`, перечисление устройств.
  Пропавший бэкенд — предупреждение с ошибкой dlopen, а не падение.
- Загрузка модели (`load_mode`, `lazy_mode`, переопределения буферов),
  токенизация, `llama_batch_ext` + `llama_process`, сэмплер, grammar
  sampler, `llama_state_seq_*`.
- Windows-путь (`AddDllDirectory`) и macOS (`@loader_path`) пишутся здесь.
  На этапе 1 они проверяются только компиляцией и CPU smoke в GitHub-раннерах.
- Тесты на `libllama` из релизных архивов и на крошечных моделях. Golden
  CPU для E4B — от `llama-cli` того же тега (`fetch-libs --tools`).
- **MTP — отдельный подэтап 1.5.M.** Цикл MTP в llama.cpp есть только в
  `common`, а нужные функции экспортируются с C++-декорацией из заголовка
  staging. Поэтому автомат драфта пишется на Go, сверяется с
  `llama-cli --spec-type draft-mtp` на крошечной модели, а на E4B
  проверяется эквивалентность greedy с драфтером и без.
- **Проверка M2 без GPU.** `per_layer_token_embd` в этом теге всегда лежит в
  CPU-буфере (это тензор входного слоя), так что M2 — штатное поведение
  upstream. Vulkan поверх программного lavapipe (Mesa) нужен, чтобы
  подтвердить это по логу размещения буферов при `gpu_layers = all`.
  Скорость не важна, важна механика.

### 1.6 Range-lock (механика)

- Отображение GGUF в память, `mlock` выбранных диапазонов. Что пин действует
  и на маппинг `libllama`, проверяется по резидентности, а не по `Locked:` в
  smaps (оно показывает только наш VMA): `madvise(MADV_PAGEOUT)` на чужой
  проекции и `mincore` — закреплённые диапазоны остаются в памяти.
- `VirtualLock` и macOS-вариант пишутся здесь же. Их механика проверяется в
  GitHub-раннерах Windows (`EmptyWorkingSet` + `QueryWorkingSetEx`) и macOS
  (только измерение): для этого не нужен ни GPU, ни большая модель.

### 1.7 Сервер v1.0 на фейковом бэкенде

- Пайплайн `core.Service` с таймингами стадий и полным `stats`.
- Chat templates. Открытый вопрос §14 закрыт так: `llama_chat_apply_template`
  не знает Gemma 4, а Jinja в llama.cpp есть только в `common`, поэтому
  шаблон Gemma 4 пишется на Go. Он побайтово сверяется с рендером
  оригинального шаблона из GGUF через `jinja2` на наборе диалогов с tools и
  thinking. Jinja на Go откладывается до второй модели.
- Парсер tool calls Gemma 4, разделение reasoning, `max_reasoning_tokens`,
  stop-последовательности.
- JSON Schema → GBNF. Порт `json_schema_to_grammar`, сверенный с эталонным
  скриптом llama.cpp на корпусе схем.
- Пул: refcount, LRU, pin, hot swap. Слоты и continuous batching. Device
  governor.
- Prompt cache как переиспользование префикса и `session_id`. Глубина
  отката зависит от `swa_full` (решение 1.4): при `true` KV обрезается до
  любой позиции, при `false` — только в пределах SWA-окна, иначе слот делает
  prefill заново. Чекпоинты SWA, как в llama-server, откладываются; снапшоты
  состояния — вместе с Qwen.
- Очередь заданий на SQLite, SSE, HMAC-вебхуки. Ключи (`key list/issue/
  remove`), rps, interactive.
- Все маршруты `openai` и `native`. Набор conformance-тестов на официальном
  OpenAI Python client против фейкового бэкенда: streaming, tools,
  `json_schema`, logprobs, формы ошибок. Тот же набор потом гоняется на
  реальной модели.
- `nanollm run` поверх того же ядра.
- Если есть время, фичи v2.0, не зависящие от железа: диалект `ollama`,
  `/v1/embeddings`.

### 1.8 Web UI

- SPA (Node 22+): Chat, Jobs, Models, Devices, Settings, Bench. Только
  публичный API, запрос ключа на первом `401`. Всё работает против фейкового
  бэкенда; экран Bench на реальном железе — этап 3.

### 1.9 Сборка и поставка

- Release workflow: архивы для пяти платформ и `-noui`, `sha256sums.txt`,
  CUDA add-on, darwin universal через `lipo`.
- `install.sh` / `install.ps1` с поведением NanoASR. systemd unit, Windows
  service, launchd. Docker-образы: CPU/Vulkan и CUDA.
- Пайплайн подписи и нотаризации macOS. Для проверки на настоящем Mac нужен
  Apple Developer ID; пайплайн можно собрать раньше, а проверить на этапе 4.

### 1.10 Инструменты оценки качества (без прогонов)

- `tools/optimize/`: харнесс KLD относительно эталонной конфигурации, формат
  eval-набора, единый JSON-отчёт на конфигурацию, `nanollm eval`.
- Корпус: ru/en текст, примеры tool calls и JSON.
- Наборы задач: русские инструкции, JSON и tools, длинный контекст, 50
  промптов для оценки человеком.
- Интерфейс для слепой оценки одним человеком: оценка 1–5 и сравнение A/B
  с клавиатуры, результаты сразу пишутся в JSON-отчёт.

### 1.11 Бенчмарк

Дизайн — в [BENCHMARKS.md](BENCHMARKS.md).

- **1.11a, сразу:** модуль `benchfmt` (формат `nanollm.bench/v1` и JSON Schema) и
  `internal/hwinfo` для трёх ОС. Модель ноутбука на реальном железе
  проверяется на этапе 3.
- **1.11b, после планировщика 1.4 и ядра 1.7:** `nanollm bench` с отдельным
  процессом на пресет, наборы `standard` и `dev`, клиент отправки по
  согласию. Smoke на E4B CPU — после биндинга 1.5; цифры VM не
  публикуются.
- **1.11c, после контрольной точки 1-C** (сервер на фейке, см.
  [STAGE1.md](STAGE1.md#порядок-и-зависимости)): сервис
  `services/bench` — API, страницы `/benchmarks`, образ, e2e в CI.
  Staging-деплой — только если владелец даст хостинг.

### Выход из этапа 1

- Тег llama.cpp и каталог закреплены. `fetch-libs` зелёный в CI.
- `plan` выдаёт планы для всех пресетов по измеренному инвентарю. Размер PLE
  и статус M2 известны.
- Биндинг проходит CI на шести целях на крошечной модели и smoke на
  `libllama` из релизных архивов на VM, включая E4B с драфтером:
  эквивалентность MTP и golden CPU записаны.
- Сервер, UI, очередь и реестр работают на фейковом бэкенде.
  Conformance-набор зелёный. `go test -race ./...` зелёный.
- Release workflow собирает все архивы. Инсталляторы проходят smoke в
  GitHub-раннерах на трёх ОС.
- Цепочка `bench --suite standard` → отправка → сервис → страница зелёная
  в e2e.

## Этап 2 — EPYC 7351P, 128 GB: CPU-инференс

**Особенности машины, которые влияют на выводы:**

- Zen 1: 16 ядер, 32 потока. AVX2 выполняется как 2 × 128 бит, AVX-512 и
  VNNI нет. CPU-ядра ggml здесь заметно медленнее, чем на ноутбучных Alder
  Lake или Zen 5. **Цифры скорости этой машины — профиль «старый сервер», а
  не прогноз для целевого ноутбука.**
- Четыре кристалла — четыре NUMA-узла, по два канала DDR4 на узел. Пропускная
  способность памяти суммарно высокая, но только при правильной раскладке.
  Нужны `numactl` / `--numa` и сравнение «один узел» против «все узлы».
  Прогон на одном узле с 6–8 потоками ближе всего к ноутбуку, но не равен
  ему.
- Без неквантованных эталонов 128 GB RAM нужны не для моделей, а для
  параллельных прогонов: eval и KLD по многим конфигурациям сразу, soak-тесты
  сервера, все пресеты `ram-*` под cgroup одновременно.
- Дисковые режимы M8 и M9 зависят от диска. Тип диска записывается в профиль
  машины. Перед холодными прогонами сбрасывается page cache.

### 2.1 Подготовка

- Linux с cgroup v2, `fetch-libs` (ubuntu x64). Проверить, что ggml выбирает
  правильный CPU-вариант для Zen 1.
- Self-hosted раннер: nightly golden-тесты и eval.

### 2.2 Гейт v0.1, CPU-часть

- Golden-тесты E4B против `llama-cli`.
- Эквивалентность MTP: greedy-вывод с драфтером и без совпадает по токенам.
  Acceptance записывается для KV f16 и q8_0.
- Round-trip состояния: сохранить, восстановить в новом слоте, продолжить,
  сравнить.

### 2.3 Режимы памяти на CPU

- M6 (direct I/O, mlock) и M9. CPU repack: проверить, применяется ли он к
  смешанным K-квантам `UD-Q4_K_XL` вообще. Если нет — он выключен везде, и
  вопрос закрыт.
- M7 и M8 с range-lock на реальной модели. Проверить, что пин покрывает
  маппинг `libllama` (риск §14).
- Direct I/O против mmap: проверить заявленное ускорение prefill на ≥ 30 %.
- Принуждение бюджетов через cgroup v2 `memory.max` в `bench`. Все пресеты
  `ram-*`, включая `ram-1g`. M10 — по остаточному принципу, как
  исследование.

### 2.4 Сервер под реальной нагрузкой

- Continuous batching и слоты на настоящей модели, hit rate prompt cache,
  `session_id`, отмена, очередь.
- Суточный soak-тест под `-race` и рост RSS. Conformance-набор на реальной
  модели.

### 2.5 O1 — качество

- Эталонная конфигурация: CPU, KV f16, без MTP. Её логиты на ru/en корпусе
  сохраняются для KLD.
- Первая оценка по гейту качества: автоматические задачи с thinking и без,
  тест длинного контекста до 16k (качество по позиции), 50 промптов на
  оценку человеком.
- KV q8_0 против f16 по KLD и по задачам. Это первая проверка, что рантайм
  не портит модель.
- **Решение:** годится ли E4B int4 как модель по умолчанию, и с thinking
  или без по умолчанию. Если не годится — это решение о модели, а не о квантизации, и
  принимается вне этого роудмапа.

### 2.6 O2 для RAM-пресетов

- Перебор потоков, `n_batch` / `n_ubatch`, типа KV, `n_ctx`.
- Измеренные планы заменяют строки `ram-*` в провизорной карте §15.

### 2.7 MTP на CPU

- Первый проход по `n_max` и `p_min`. Ожидание по §13 скромное: здесь
  решается, выключен ли MTP на CPU по умолчанию и почему.

### 2.8 Бенчмарк на реальном CPU

- Первые настоящие прогоны `bench --suite standard`: повторы и разброс,
  проверка бюджета времени, принуждение strict через cgroup.
- CPU-потолки для проверки правдоподобия в сервисе.
- Отправки этой машины помечаются vendor-verified, класс «сервер».

### Выход из этапа 2

- Golden-тесты, эквивалентность MTP и round-trip зелёные на CPU.
- M6–M9 работают и принуждаются через cgroup. У каждого `ram-*` пресета есть
  измеренный план.
- Есть эталонная конфигурация и базовый отчёт качества, включая оценку
  человеком. Порог KLD откалиброван.
- Сервер выдерживает суточную нагрузку на реальной модели.

## Этап 3 — i7-12700H + RTX 3070 Ti Laptop: целевая среда

**Особенности машины:**

- 6 P-ядер и 8 E-ядер, 20 потоков, AVX2 + AVX-VNNI, AVX-512 нет. Правило
  «потоки = физические ядра» на гибридном CPU не очевидно. Сравнить «только
  P-ядра», «P+E» и привязку потоков.
- RTX 3070 Ti Laptop: 8 GB GDDR6, sm_86. Часть VRAM занимают драйвер и
  рабочий стол, если экран выводится через дискретку. `vram-8g` может не
  поместиться целиком, а `auto` должен смотреть на свободную память, а не на
  общую. Проверить с MUX/Optimus в обоих положениях, если MUX есть.
- Iris Xe тоже виден как Vulkan-устройство. Это бесплатный тест выбора
  устройства: `auto` должен выбирать дискретку, `vulkan1` — работать явно.
- 32 GB RAM: E4B помещается в M6, так что CPU-цифры этой машины — реальный
  ориентир для CPU-пресетов на ноутбуке.
- Ноутбук: бенчмарки идут на фиксированном профиле питания, от сети. Отдельно
  — короткий прогон от батареи и замер троттлинга.

**Windows и WSL2.** Основная платформа — Windows. WSL2 даёт Linux-сборку на
том же железе, но с отличиями, которые надо учитывать в выводах:

- CUDA в WSL2 работает через драйвер Windows и близка к нативной. Это
  основной Linux GPU-прогон.
- Vulkan в WSL2 идёт через трансляцию Mesa в D3D12 (dzn), а не через
  нативный драйвер NVIDIA. Linux Vulkan-цифры отсюда не представительны.
  Linux + Vulkan на реальном GPU остаётся непокрытым, если ни одна машина
  этапа 4 не работает под Linux.
- По умолчанию WSL2 получает половину RAM, лимит задаётся в `.wslconfig`.
  Это удобно для `ram-*` пресетов, но лимит пишется в профиль машины.
- Модели лежат в файловой системе WSL (ext4 внутри VHDX). С `/mnt/c` чтение
  идёт через 9p и в разы медленнее, а M8 и M9 там бессмысленны.
- cgroup v2 и `mlock` в WSL2 работают. Range-lock и принуждение бюджетов
  проверяются здесь заново, но не заменяют нативный Linux этапа 2.

### 3.1 Подготовка

- Windows: `fetch-libs` для win-vulkan-x64, CUDA add-on, загрузка библиотек
  только по абсолютному пути, `AddDllDirectory`.
- `devices` показывает CUDA0, Vulkan0 (дискретка) и Vulkan1 (iGPU).
- WSL2: linux-amd64 с CUDA add-on.
- Self-hosted GPU-раннер на Windows, второй — в WSL2.

### 3.2 Гейт v0.1, GPU-часть

- Golden-тесты на CUDA (Windows и WSL2) и Vulkan (Windows), эквивалентность
  MTP на GPU, acceptance по типам KV.
- KLD против эталонной конфигурации этапа 2 для каждого GPU-бэкенда.
- Flash attention с драфтером на CUDA. README драфтера у Unsloth требует
  `-fa off`: с FA драфт-модель падала в CUDA-ядре flash attention.
  Проверить на закреплённом теге. Если не исправлено, планировщик выключает
  FA для пар с MTP на CUDA, и O3 меряет обе конфигурации.
- **Доказательство M2:** при `gpu_layers = all` PLE остаётся в RAM (в этом
  теге — штатно, этап 1 подтвердил это на lavapipe), ядро на GPU, скорость и
  потребление VRAM соответствуют плану. Если upstream это поведение сломает,
  планировщик пропускает M2 и M3, а исправление уходит в llama.cpp (§14).
- M3 и M4 с перебором N.
- После этого **гейт v0.1 закрыт** на CPU, Vulkan и CUDA.

### 3.3 Windows-механика

- `VirtualLock` range-lock с квотой working set
  (`SetProcessWorkingSetSize`), Job Objects для принуждения бюджетов, direct
  I/O на NTFS.
- Служба, `install.ps1`, обновление на месте.
- Вопрос к решению: подпись Authenticode, иначе SmartScreen и Defender будут
  ругаться на неподписанный бинарь.

### 3.4 O2 для GPU-пресетов

- `vram-2g` … `vram-8g` и комбинированные пресеты: измеренные планы, N для
  M4, тип KV, `n_ctx`.
- **Решение:** нужен ли CUDA add-on или Vulkan достаточно близок на NVIDIA
  (открытый вопрос §14). Решается по данным `bench` на Windows.

### 3.5 O3 — MTP

- Гейт на каждую пару устройство × пресет: ускорение ≥ 1,2× при temperature
  0.7, без потери многослотовой пропускной способности, токен-в-токен greedy,
  ненулевой acceptance на выбранном типе KV.
- Комбинация n-gram и MTP на шаблонном выводе и JSON. Пары, не прошедшие
  гейт, выходят с выключенным MTP, и план объясняет почему.

### 3.6 Продукт на целевой машине

- Регулярная работа через UI и OpenAI-клиенты: всё, что неудобно, чинится до
  релиза.

### 3.7 Бенчмарк на целевом ноутбуке

- GPU-пресеты в `bench`, power limit GPU, состояние «сеть или батарея».
- `hwinfo` на реальном Windows: SMBIOS даёт модель ноутбука; в WSL2 — через
  interop с хостом.
- Экран Bench в UI на реальном железе. Набор `standard --quick` укладывается
  в 15 минут.
- Первые публичные результаты на nano.llmto.day, если сервис развёрнут.

### 3.8 Кандидат v1.0

- Conformance-набор зелёный на реальной модели на CUDA и Vulkan.
- Архивы windows-amd64 и linux-amd64 ставятся с нуля и обновляются на месте
  (Windows и WSL2).

### Выход из этапа 3

- Гейт v0.1 закрыт на CPU, Vulkan и CUDA. M2 доказан или исключён с
  объяснением.
- У каждого GPU-пресета есть измеренный план. MTP включён только там, где
  прошёл O3. GPU-бэкенды в пределах порога KLD.
- Кандидат v1.0 работает на целевом железе в Windows и WSL2.

## Этап 4 — Mac, Ryzen AI, Intel, Core i5-1035G

### Mac (Apple Silicon) — финальные тесты

- Golden-тесты и KLD на Metal, эквивалентность MTP. Это последний бэкенд
  гейта v0.1, и его прохождение — условие релиза v1.0 на macOS.
- Пресеты `uma-*`, M3 через file-backed буферы Metal без копирования, предел
  `iogpu.wired_limit_mb`. `uma-8g` требует машину минимум с 16 GB.
- Подпись и нотаризация, проверенные на чистой машине через Gatekeeper.
  launchd, `install.sh`, darwin universal. Для x86_64-слайса без Intel Mac
  остаётся только CPU smoke в CI.
- Если на Metal найдётся что-то, что требует изменений в ядре, релиз v1.0
  выходит без macOS, а darwin догоняет его патчем. Это лучше, чем держать
  весь релиз.
- O5: MLX против Metal через ggml. **Решение по v3.0:** MLX делается, только
  если он выигрывает. Квантизация для MLX — тоже int4.

### Ryzen AI

Предположение: серия Ryzen AI 300 — Zen 5 с AVX-512, iGPU RDNA 3.5, NPU
XDNA 2. Точную модель надо уточнить.

- CPU: вариант ggml с AVX-512 и сравнение с 12700H.
- Vulkan на iGPU с общей памятью. Что значат `vram-*` пресеты, если VRAM — это
  выделенный в BIOS кусок RAM плюс GTT, и куда считать бюджет. Вероятно, сюда
  нужен UMA-учёт, как на Mac.
- HIP/ROCm на iGPU — по возможности, не обязательно.
- **v2.0, NPU AMD:** бэкенд ORT GenAI через purego и VitisAI из сборок AMD.
  Экспорт E4B в int4 через model builder и квантование AMD под NPU (O4).

### Intel

Модель уточнить. Для NPU нужен Core Ultra (Meteor Lake, Lunar Lake или Arrow
Lake).

- **v2.0, NPU Intel:** тот же бэкенд ORT GenAI с OpenVINO EP, экспорт E4B в
  int4 и квантование через инструменты Intel (O4).
- iGPU Arc через Vulkan, по возможности SYCL.
- В релизах llama.cpp есть сборки с бэкендом OpenVINO (`ubuntu-openvino`,
  `win-openvino`). Проверить, видит ли он NPU Intel. Если да, это путь к NPU
  через тот же `libllama` и тот же GGUF, без экспорта в ORT GenAI, и он
  проверяется раньше ORT-бэкенда.
- Общий бэкенд с AMD означает, что второй вендор — это в основном новый EP и
  новый экспорт, а не новый код.

### Core i5-1035G (Ice Lake)

- 4 ядра, 8 потоков, AVX-512 с VNNI, iGPU Gen11, обычно 8–16 GB RAM и
  медленный диск, TDP 15 W. Это **нижняя граница железа**.
- Пресеты `ram-2g` … `ram-4g`, режимы M7 и M8, где упираемся в диск.
  Троттлинг на длинной генерации.
- Vulkan на Gen11 для `vram-2g` / `vram-3g`. Проверить правило §3 «auto: GPU,
  затем CPU»: на слабом iGPU оно может быть хуже CPU. Тогда `auto` должен
  выбирать по данным `bench`, а не по типу устройства.
- Установка на «типичный офисный ноутбук»: время до первого ответа после
  `install`.

### Бенчмарк на всех машинах этапа

- `hwinfo` на Mac (`hw.model`, число ядер GPU) и пресеты `uma-*` в `bench`;
  Ryzen AI, Intel и i5-1035G — как разные классы ноутбуков.
- Публичный запуск страницы Benchmarks вместе с релизом v1.0. Результаты на
  NPU появляются с v2.0.

### Выход из этапа 4

- Релиз v1.0: архивы на все пять платформ, conformance зелёный, `verified[]`
  заполнен для всех проверенных пар.
- v2.0, если хотя бы один из VitisAI или OpenVINO проходит гейт на E4B. Иначе
  v2.0 выходит без NPU, с `ollama`, embeddings и мультимодальностью, а NPU
  переносится.
- Решение по v3.0 принято на основе данных.

### Что не покрыто ни одной машиной

- Windows ARM64 и Snapdragon (QNN), Linux ARM64. CPU smoke на ARM64 можно
  гонять в GitHub-раннерах (`windows-11-arm`, `ubuntu-24.04-arm`).
- Нативный Linux с Vulkan на реальном GPU, если ни одна машина этапа 4 не
  работает под Linux.
- Дискретные AMD GPU (HIP), Intel Mac.

Всё это выходит без отметки в `verified[]` и не выбирается автоматически.

## Когда снимается каждый риск

| Риск (§14) | Где снимается раньше всего |
| --- | --- |
| Неизвестна доля PLE в E4B | Этап 1: заголовок GGUF |
| PLE не остаётся в RAM при `gpu_layers = all` (в `b11600` он штатно лежит в CPU-буфере как тензор входного слоя; риск — что upstream это изменит) | Этап 1 функционально (lavapipe), этап 3 на реальном GPU, при каждом обновлении тега — проверка размещения по логу |
| `GGML_ABORT` и исключения C++ в libllama роняют весь процесс | Этап 1: входы проверяются в Go до вызова, сервис перезапускает супервизор, `bench` гоняет каждый пресет в отдельном процессе |
| API MTP в llama.cpp нестабилен: заголовок staging, функции с C++-декорацией, цикл только в `common` | Этап 1: автомат на Go, проверка имён символов и сверка с `llama-cli` при каждом обновлении тега; предложить upstream `extern "C"` |
| Range-lock не покрывает маппинг libllama | Этап 1 на Linux, этап 2 на реальной модели, этап 3 на Windows, этап 4 на macOS |
| Сменилась раскладка релизных архивов llama.cpp | Этап 1: `fetch-libs` в CI |
| E4B int4 недостаточно хорош как модель по умолчанию | Этап 2 (O1), оценка человеком |
| Рантайм портит модель (KV q8_0, GPU-бэкенд, обновление тега) | Этап 2 для CPU и KV, этап 3 для GPU, на каждом обновлении — KLD против эталона |
| MTP не ускоряет | Этап 2 для CPU, этап 3 для GPU (O3) |
| Metal и подпись macOS | Этап 1 — пайплайн и CPU smoke в CI, этап 4 — реальный Metal и Gatekeeper |
| Несовпадение драйвера CUDA | Этап 3 |

| Бенчмарк: подделка или перекос результатов | Этап 1 — потолок правдоподобия, MAD в когорте, лимиты, модерация; этапы 2–3 — калибровка потолков на реальном железе, vendor-verified. Подпись доказывает только владение |
| Бенчмарк: персональные данные (GDPR, 152-ФЗ) | Этап 1 — минимум полей, согласие с версией, IP не хранятся, анонимный режим, удаление отправки; юридическая проверка до первых публичных результатов (этап 3) |
| Бенчмарк: несравнимые цифры | Этап 1 — версия набора, когорты, отдельный процесс на пресет; этап 2 — разброс на реальном железе |
