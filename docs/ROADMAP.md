# NanoLLM — роудмап разработки

Роудмап раскладывает вехи спецификации (v0.1 → v1.0 → v2.0 → v3.0 и
оптимизационные стадии O1–O5, SPEC §14) по четырём средам, в которых идёт
разработка. Номера `§N` ссылаются на NanoLLM Development Specification.

Правило одно: **этап закрывается только тем, что на его железе можно
доказать.** Всё, что не зависит от скорости и от конкретного ускорителя,
делается раньше, чем появится нужная машина. Всё, что зависит, начинается за
интерфейсом с подделкой и доказывается позже на реальном железе.

## Карта этапов

| Этап | Среда | Что закрывает |
| --- | --- | --- |
| 1 | Текущая VM: 4 vCPU, 15 GB RAM, ~29 GB диска, без GPU | Весь код v0.1 и v1.0, которому не нужна скорость: биндинг, GGUF-инвентарь, планировщик, сервер целиком на фейковом бэкенде, реестр, UI, сборка и инсталляторы. Инструменты O1 |
| 2 | AMD EPYC 7351P, 128 GB RAM, без GPU | CPU-часть гейта v0.1, режимы M6–M9 и пресеты `ram-*`, всё O1 (качество, выбор варианта по умолчанию), O2 для RAM-пресетов, fallback Qwen3.5-9B, нагрузка на сервер |
| 3 | Core i7-12700H, RTX 3070 Ti Laptop 8 GB, 32 GB RAM — целевая среда | CUDA/Vulkan-часть гейта v0.1, доказательство M2 (PLE override), пресеты `vram-*` и комбинированные, O2 для GPU, O3 (MTP), Windows целиком, кандидат v1.0 |
| 4 | Mac, Ryzen AI, Core i5-1035G | Metal-часть гейта v0.1, `uma-*`, подпись macOS, релиз v1.0 на пяти платформах, v2.0 (NPU через VitisAI), решение по v3.0 (MLX), нижняя граница железа |

Две вещи из этой карты расходятся со спецификацией. Их надо решить заранее.

- **Гейт v0.1 требует golden-тестов на CPU, Vulkan, CUDA и Metal.** Metal есть
  только на этапе 4. Варианты: (а) получить Mac на день-два в конце этапа 3;
  (б) разделить гейт на v0.1 (CPU/Vulkan/CUDA) и v0.1-metal. Рекомендую (а):
  Metal-путь отличается от остальных (unified memory, M3 без копирования),
  и его сюрпризы лучше узнать до того, как сервер v1.0 будет закончен.
- **Единственный NPU в списке — Ryzen AI.** Гейт v2.0 («хотя бы один NPU-вендор
  проверен на E4B») держится на одном устройстве и на том, что AMD отдаёт
  onnxruntime-genai со сборкой VitisAI. Intel (OpenVINO) и Qualcomm (QNN)
  проверить не на чем.

## Сквозные принципы

- **Фейковый бэкенд.** `internal/backend/fake` реализует `backend.Model`:
  токенизатор по байтам и детерминированные логиты по сценарию. Он даёт
  разработать и прогнать под `-race` весь сервер на этапе 1: пул, слоты,
  continuous batching, prompt cache, очередь, диалекты и UI. Реальный бэкенд
  подключается под те же тесты.
- **Golden-тесты — это данные.** Эталонные токены от `llama-cli` того же
  закреплённого тега лежат в `testdata/golden/<tag>/`. Любая машина прогоняет
  их и пишет результат в `verified[]` манифеста.
- **Бенчмарки с профилем машины.** JSON из `nanollm bench` хранится в
  `bench/results/<machine>/` вместе с CPU, памятью, диском, ОС и драйверами.
  Цифры одной машины никогда не переносятся на другую.
- **Каждая новая машина становится self-hosted раннером CI.** Это нужно, чтобы
  обновление llama.cpp прогоняло golden-тесты везде, где они уже проходили.
- **Оптимизация не обгоняет качество.** Ни один пресет не тюнингуется, пока в
  O1 не выбран вариант по умолчанию (§13: квантованный E4B должен пройти
  русский гейт).

## Этап 1 — текущая VM: разработка без полноценного инференса

**Что есть.** 4 vCPU, 15 GB RAM, ~29 GB свободного диска, без GPU. Проверено:
Hugging Face доступен (API репозиториев, загрузки, range-запросы), `git`
к llama.cpp работает. Релизные архивы llama.cpp с GitHub отсюда не качаются
(403 через прокси), зато доступны из GitHub Actions.

Это значит, что этап не «без инференса», а **без инференса, по которому можно
судить**. `libllama` собирается из исходников закреплённого тега (CPU, cmake),
крошечные модели и даже E4B запускаются для smoke-тестов (единицы токенов в
секунду). Выводы о скорости и качестве здесь не делаются.

### 1.1 Закрепление зависимостей

- Выбрать тег llama.cpp ≥ `b9568`, записать в `scripts/llama.cpp.tag`.
- Job в GitHub Actions, который скачивает релизные архивы этого тега, сверяет
  имена в `fetch-libs.sh` с реальными и записывает `scripts/libs.sha256`.
  Дальше `fetch-libs` проверяется в CI на каждом пуше.
- Закрепить каталог: коммит репозитория, размеры и SHA-256 файлов через HF API
  (LFS-метаданные дают sha256 без скачивания). После этого `Pinned()` у всех
  трёх моделей возвращает true.

### 1.2 Реестр

- Загрузчик: докачка, проверка SHA-256 до использования, зеркала
  (`registry.mirrors`), `strict_license`.
- `models pull / list / rm`. `init` скачивает E4B вместе с драфтером.
- `POST /api/v1/models/{id}/download` с прогрессом по SSE.

### 1.3 GGUF-инвентарь

- Парсер заголовка GGUF на Go: метаданные, chat template, тензоры со
  смещениями.
- Классификатор групп G0–G7 по именам тензоров `gemma4`, `gemma4-assistant`,
  `qwen35`.
- `models inspect --tensors` заполняет `tensors[]` в каталоге.
- **Это первый ответ на главный открытый вопрос §4:** сколько байт в E4B
  занимает PLE, а сколько ядро. Для ответа нужен только заголовок файла.
  Провизорная карта пресетов (§15) пересчитывается сразу, а не после O1.

### 1.4 Планировщик

- Учёт байт по инвентарю. KV по формуле архитектуры: SWA 512, общий KV на
  18 из 42 слоёв у E4B, DeltaNet-состояние у Qwen. Оценка compute-буферов,
  которая калибруется на этапах 2–3.
- Порядок M1 → M2 → M3 → M4 → M6 → M7 → M8 → M9, пол `n_ctx = 4096`, один
  слот, отказ с недостачей в байтах.
- `nanollm plan <model> --preset <name>`. Табличные тесты на все 19 пресетов
  × 3 модели.

### 1.5 Биндинг к libllama

- Генератор биндинга по `llama.h` закреплённого тега (`tools/bindgen`).
  Проверка build number при старте: несовпадение — понятная ошибка.
- `ggml_backend_load_all_from_path(<lib>)`, перечисление устройств.
  Пропавший бэкенд — предупреждение, а не падение.
- Загрузка модели, токенизация, decode батча, сэмплер, grammar sampler,
  `llama_state_seq_*`, MTP-драфтер.
- Windows-путь (`AddDllDirectory`) и macOS (`@loader_path`) пишутся здесь.
  На этапе 1 они проверяются только компиляцией и CPU smoke в GitHub-раннерах.
- Тесты на `libllama`, собранной из исходников, и на крошечных моделях.
  Один прогон E4B с драфтером: доказать, что binding доходит до MTP.
- **Ранняя проверка M2 без GPU.** Vulkan в llama.cpp работает поверх
  программного lavapipe (Mesa), это ожидаемо, но надо проверить. Тогда можно
  функционально проверить, что PLE-тензоры остаются в host-буфере при
  `gpu_layers = all`. Скорость не важна, важна механика. Если получится,
  главный риск гейта v0.1 снимается до появления GPU.

### 1.6 Range-lock (механика)

- Отображение GGUF в память, `mlock` выбранных диапазонов, проверка через
  `/proc/self/smaps` (`Locked:`), что пин действует и на маппинг `libllama`.
- `VirtualLock` и macOS-вариант пишутся здесь же. Их механика проверяется в
  GitHub-раннерах Windows и macOS: для этого не нужен ни GPU, ни большая модель.

### 1.7 Сервер v1.0 на фейковом бэкенде

- Пайплайн `core.Service` с таймингами стадий и полным `stats`.
- Chat templates. Здесь закрывается открытый вопрос §14: реализация Jinja
  на Go или встроенные шаблоны llama.cpp. Рекомендация: Jinja на Go,
  проверенная по выходу `apply_chat_template` из `transformers` на наборе
  диалогов с tools и thinking. Встроенный в llama.cpp рендер слабее на tools.
- Парсеры tool calls (Gemma 4, Qwen3.5), разделение reasoning,
  `max_reasoning_tokens`, stop-последовательности.
- JSON Schema → GBNF. Порт `json_schema_to_grammar`, сверенный с эталонным
  скриптом llama.cpp на корпусе схем.
- Пул: refcount, LRU, pin, hot swap. Слоты и continuous batching. Device
  governor. Prompt cache с префиксами, снапшоты состояния и `session_id`.
- Очередь заданий на SQLite, SSE, HMAC-вебхуки. Ключи (`key list/issue/
  remove`), rps, interactive.
- Все маршруты `openai` и `native`. Набор conformance-тестов на официальном
  OpenAI Python client против фейкового бэкенда: streaming, tools,
  `json_schema`, logprobs, формы ошибок. Тот же набор потом гоняется на
  реальной модели.
- `nanollm run` поверх того же ядра.
- Если есть время, фичи v2.0, не зависящие от железа: диалект `ollama`,
  `/v1/embeddings`.

### 1.8 Web UI

- SPA (Node 22+): Chat, Jobs, Models, Devices, Settings. Только публичный API,
  запрос ключа на первом `401`. Всё работает против фейкового бэкенда.

### 1.9 Сборка и поставка

- Release workflow: архивы для пяти платформ и `-noui`, `sha256sums.txt`,
  CUDA add-on, darwin universal через `lipo`.
- `install.sh` / `install.ps1` с поведением NanoASR. systemd unit, Windows
  service, launchd. Docker-образы: CPU/Vulkan и CUDA.
- Пайплайн подписи и нотаризации macOS. Спека требует его с v0.1, поэтому
  Apple Developer ID нужен уже здесь.

### 1.10 Инструменты оптимизации (без прогонов)

- `tools/optimize/`: харнесс KLD (`llama-perplexity --kl-divergence`),
  формат eval-набора, единый JSON-отчёт на вариант, `nanollm eval`.
- Калибровочный корпус: ru/en текст, анонимизированные диалоги Эры,
  примеры tool calls и JSON.
- Русский набор инструкций, задачи Эры, 200 промптов для слепого
  side-by-side и простой интерфейс для асессоров.

### Выход из этапа 1

- Тег llama.cpp и каталог закреплены. `fetch-libs` зелёный в CI.
- `plan` выдаёт планы для всех пресетов по измеренному инвентарю. Размер PLE
  известен.
- Биндинг проходит smoke на собранной из исходников `libllama`, включая E4B
  с драфтером.
- Сервер, UI, очередь и реестр работают на фейковом бэкенде.
  Conformance-набор зелёный. `go test -race ./...` зелёный.
- Release workflow собирает все архивы. Инсталляторы проходят smoke в
  GitHub-раннерах на трёх ОС.

## Этап 2 — EPYC 7351P, 128 GB: CPU-инференс

**Особенности машины, которые влияют на выводы:**

- Zen 1: 16 ядер, 32 потока. AVX2 выполняется как 2 × 128 бит, AVX-512 и
  VNNI нет. CPU-ядра ggml здесь заметно медленнее, чем на ноутбучных Alder
  Lake или Zen 5. **Цифры скорости этой машины — профиль «старый сервер», а
  не прогноз для целевого ноутбука.**
- Четыре кристалла — четыре NUMA-узла, по два канала DDR4 на узел. Пропускная
  способность памяти суммарно высокая, но только при правильной раскладке.
  Нужны `numactl` / `--numa` и сравнение «один узел» против «все узлы».
  Прогон на одном узле с 6–8 потоками ближе всего к ноутбуку, но не равен
  ему.
- 128 GB RAM — главное достоинство. Здесь помещаются BF16-эталоны E4B
  (~16 GB) и 12B (~24 GB) в `transformers`, F16 GGUF и параллельные прогоны.
- Дисковые режимы M8 и M9 зависят от диска. Тип диска записывается в профиль
  машины. Перед холодными прогонами сбрасывается page cache.

### 2.1 Подготовка

- Linux с cgroup v2, `fetch-libs` (ubuntu x64). Проверить, что ggml выбирает
  правильный CPU-вариант для Zen 1.
- Self-hosted раннер: nightly golden-тесты и eval.

### 2.2 Гейт v0.1, CPU-часть

- Golden-тесты E4B, 12B и Qwen3.5-9B против `llama-cli`.
- Эквивалентность MTP: greedy-вывод с драфтером и без совпадает по токенам.
  Acceptance записывается для KV f16 и q8_0.
- Round-trip состояния, снапшоты DeltaNet для Qwen.

### 2.3 Режимы памяти на CPU

- M6 (direct I/O, mlock, repack вкл/выкл) и M9.
- M7 и M8 с range-lock на реальной модели. Проверить, что пин покрывает
  маппинг `libllama` (риск §14).
- Direct I/O против mmap: проверить заявленное ускорение prefill на ≥ 30 %.
- Принуждение бюджетов через cgroup v2 `memory.max` в `bench`. Все пресеты
  `ram-*`, включая `ram-1g`. M10 — по остаточному принципу, как
  исследование.

### 2.4 Сервер под реальной нагрузкой

- Continuous batching и слоты на настоящей модели, hit rate prompt cache,
  `session_id`, отмена, очередь.
- Суточный soak-тест под `-race` и рост RSS. Conformance-набор на реальной
  модели.

### 2.5 O1 — качество

- Эталоны: Google `qat-q4_0-unquantized` и не-QAT instruct, прогнанные
  через `transformers` и через F16 GGUF. Оба должны совпасть до любых
  сравнений.
- KLD (среднее и p99) и top-1 agreement для Unsloth `UD-Q4_K_XL`, Google
  `Q4_0` и Q8_0 — отдельно для E4B и 12B.
- Задачи: ru/en инструкции, JSON, tools, thinking вкл/выкл, набор Эры.
- Слепой side-by-side на 200 русских промптах против Q8_0. Для него нужны
  люди.
- **Решение:** вариант по умолчанию (открытый вопрос §14). Если QAT Q4 не
  проходит, по умолчанию идёт Q8_0, и пересчитывается карта пресетов.
- Qwen3.5-9B: imatrix `Q4_K_M` по общему корпусу. Тест дрейфа качества по
  позиции до 16k.

### 2.6 O2 для RAM-пресетов

- Перебор потоков, `n_batch` / `n_ubatch`, типа KV, `n_ctx`. CPU repack через
  вариант `Q4_0`.
- Измеренные планы заменяют строки `ram-*` в провизорной карте §15.

### 2.7 MTP на CPU

- Первый проход по `n_max` и `p_min`. Ожидание по §13 скромное: здесь
  решается, выключен ли MTP на CPU по умолчанию и почему.

### Выход из этапа 2

- Golden-тесты и эквивалентность MTP зелёные на CPU для всех трёх моделей.
- M6–M9 работают и принуждаются через cgroup. У каждого `ram-*` пресета есть
  измеренный план.
- Вариант E4B по умолчанию выбран по результатам гейта качества, а не по
  средним значениям.
- Сервер выдерживает суточную нагрузку на реальной модели.

## Этап 3 — i7-12700H + RTX 3070 Ti Laptop: целевая среда

**Особенности машины:**

- 6 P-ядер и 8 E-ядер, 20 потоков, AVX2 + AVX-VNNI, AVX-512 нет. Правило
  «потоки = физические ядра» на гибридном CPU не очевидно. Сравнить «только
  P-ядра», «P+E» и привязку потоков.
- RTX 3070 Ti Laptop: 8 GB GDDR6, sm_86. Часть VRAM занимают драйвер и
  рабочий стол, если экран выводится через дискретку. `vram-8g` может не
  поместиться целиком, а `auto` должен смотреть на свободную память, а не на
  общую. Проверить с MUX/Optimus в обоих положениях.
- Iris Xe тоже виден как Vulkan-устройство. Это бесплатный тест выбора
  устройства: `auto` должен выбирать дискретку, `vulkan1` — работать явно.
- 32 GB RAM: все модели помещаются в M6, так что CPU-цифры этой машины —
  реальный ориентир для CPU-пресетов на ноутбуке.
- Ноутбук: бенчмарки идут на фиксированном профиле питания, от сети. Отдельно
  — короткий прогон от батареи и замер троттлинга.
- ОС: Windows 11 как основная. Linux на том же железе (dual boot или live
  USB) — для CUDA и Vulkan на Linux. WSL2 не считается.

### 3.1 Подготовка на Windows

- `fetch-libs` для win-vulkan-x64, CUDA add-on, загрузка библиотек только по
  абсолютному пути, `AddDllDirectory`.
- `devices` показывает CUDA0, Vulkan0 (дискретка) и Vulkan1 (iGPU).
- Self-hosted GPU-раннер.

### 3.2 Гейт v0.1, GPU-часть

- Golden-тесты на CUDA и Vulkan, эквивалентность MTP на GPU, acceptance по
  типам KV.
- **Доказательство M2:** PLE через tensor buffer override на CPU при
  `gpu_layers = all`. Если не выходит — планировщик пропускает M2 и M3, а
  поддержка уходит в upstream llama.cpp (§14).
- M3 и M4 с перебором N.

### 3.3 Windows-механика

- `VirtualLock` range-lock с квотой working set
  (`SetProcessWorkingSetSize`), Job Objects для принуждения бюджетов, direct
  I/O на NTFS.
- Служба, `install.ps1`, обновление на месте.
- Вопрос к решению: подпись Authenticode, иначе SmartScreen и Defender будут
  ругаться на неподписанный бинарь.

### 3.4 O2 для GPU-пресетов

- `vram-2g` … `vram-8g` и комбинированные пресеты: измеренные планы, N для
  M4, тип KV, `n_ctx`.
- **Решение:** нужен ли CUDA add-on или Vulkan достаточно близок на NVIDIA
  (открытый вопрос §14). Решается по данным `bench`.

### 3.5 O3 — MTP

- Гейт на каждую пару устройство × пресет для E4B и 12B: ускорение ≥ 1,2× при
  temperature 0.7, без потери многослотовой пропускной способности,
  токен-в-токен greedy, ненулевой acceptance на выбранном типе KV.
- Комбинация n-gram и MTP на шаблонном выводе и JSON. Пары, не прошедшие
  гейт, выходят с выключенным MTP, и план объясняет почему.

### 3.6 Продукт на целевой машине

- Сценарий Эры: TTFT для голоса, thinking выключен, prompt cache для
  скриптов звонков. Если нужен диалект `era`, решение принимается здесь.
- Регулярная работа через UI и OpenAI-клиенты: всё, что неудобно, чинится до
  релиза.

### 3.7 Кандидат v1.0

- Conformance-набор зелёный на реальной модели на CUDA и Vulkan.
- Архивы linux-amd64 и windows-amd64 ставятся с нуля и обновляются на месте.
  Проверено на Windows и на Linux.

### Выход из этапа 3

- Golden-тесты зелёные на CPU, Vulkan и CUDA. M2 доказан или исключён с
  объяснением.
- У каждого GPU-пресета есть измеренный план. MTP включён только там, где
  прошёл O3.
- Кандидат v1.0 работает на Windows и Linux на целевом железе.

## Этап 4 — Mac, Ryzen AI, Core i5-1035G

### Mac (Apple Silicon)

- Golden-тесты на Metal: **формально закрывают гейт v0.1**, если Mac не
  появился раньше.
- Пресеты `uma-*`, M3 через file-backed буферы Metal без копирования, предел
  `iogpu.wired_limit_mb`. `uma-8g` требует машину минимум с 16 GB.
- Подпись и нотаризация, проверенные на чистой машине через Gatekeeper.
  launchd, `install.sh`, darwin universal. Для x86_64-слайса без Intel Mac
  остаётся только CPU smoke в CI.
- O5: MLX против Metal через ggml на фронте Парето. **Решение по v3.0:**
  MLX делается, только если он выигрывает.

### Ryzen AI

Предположение: серия Ryzen AI 300 — Zen 5 с AVX-512, iGPU RDNA 3.5, NPU
XDNA 2. Точную модель надо уточнить.

- CPU: вариант ggml с AVX-512 и сравнение с 12700H.
- Vulkan на iGPU с общей памятью. Что значат `vram-*` пресеты, если VRAM — это
  выделенный в BIOS кусок RAM плюс GTT, и куда считать бюджет. Вероятно, сюда
  нужен UMA-учёт, как на Mac.
- HIP/ROCm на iGPU — по возможности, не обязательно.
- **v2.0:** бэкенд ORT GenAI через purego и VitisAI из сборок AMD. Экспорт
  E4B через model builder, O4 (int4, квантование под NPU). Если E4B не
  экспортируется, NPU откладывается, а не меняется модель (§3).

### Core i5-1035G (Ice Lake)

- 4 ядра, 8 потоков, AVX-512 с VNNI, iGPU Gen11, обычно 8–16 GB RAM и
  медленный диск, TDP 15 W. Это **нижняя граница железа**.
- Пресеты `ram-2g` … `ram-4g`, режимы M7 и M8, где упираемся в диск.
  Троттлинг на длинной генерации.
- Vulkan на Gen11 для `vram-2g` / `vram-3g`. Проверить правило §3 «auto: GPU,
  затем CPU»: на слабом iGPU оно может быть хуже CPU. Тогда `auto` должен
  выбирать по данным `bench`, а не по типу устройства.
- Установка на «типичный офисный ноутбук»: время до первого ответа после
  `install`.

### Выход из этапа 4

- Релиз v1.0: архивы на все пять платформ, гейт conformance зелёный,
  `verified[]` заполнен для всех проверенных пар.
- v2.0, если VitisAI проходит гейт на E4B. Иначе v2.0 выходит без NPU, с
  `ollama`, embeddings и мультимодальностью, а NPU переносится.
- Решение по v3.0 принято на основе данных.

### Что не покрыто ни одной машиной

Windows ARM64 и Snapdragon (QNN), Linux ARM64, Intel Core Ultra NPU
(OpenVINO), дискретные AMD GPU (HIP), Intel Mac. CPU smoke на ARM64 можно
гонять в GitHub-раннерах (`windows-11-arm`, `ubuntu-24.04-arm`). Остальное
выходит без отметки в `verified[]` и не выбирается автоматически.

## Когда снимается каждый риск

| Риск (§14) | Где снимается раньше всего |
| --- | --- |
| Неизвестна доля PLE в E4B | Этап 1: заголовок GGUF |
| PLE не размещается отдельно через tensor override | Этап 1 функционально (lavapipe), этап 3 на реальном GPU |
| Range-lock не покрывает маппинг libllama | Этап 1 на Linux, этап 2 на реальной модели, этап 3 на Windows, этап 4 на macOS |
| Сменилась раскладка релизных архивов llama.cpp | Этап 1: `fetch-libs` в CI |
| QAT Q4 не проходит русский гейт | Этап 2 (O1) |
| MTP не ускоряет | Этап 2 для CPU, этап 3 для GPU (O3) |
| Подпись macOS | Этап 1 — пайплайн, этап 4 — реальный Gatekeeper |
| Несовпадение драйвера CUDA | Этап 3 |
| Нет VitisAI или E4B не экспортируется в ORT GenAI | Этап 4, единственная попытка |
